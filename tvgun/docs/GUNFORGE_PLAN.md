## 0. 已确定的前提

| 项 | 结论 |
|---|---|
| 游戏类型 | 只做光枪游戏 |
| 玩家 | 自己和朋友在家玩，不商业发行 |
| 首款形态 | 分镜式（定点站位，敌人从掩体后出现），全 3D 轨道以后再说 |
| AI 服务 | 图片统一使用当前内置 GPT 图像工具；音频另行接入 |
| 美术大方向 | 第一版只做 2D；美术是最重要的部分，先单独验证（阶段 0A） |
| 分工 | 首款的世界观、风格和玩法由 AI 提出、你来定；其余全部由 AI 完成，你只在审核点介入 |

不做：多人联网、移动端、商业发行、上架合规。

## 1. 总体思路

1. **框架尽量复用，游戏主要是数据。** 先用 AI 写一个通用的 Godot 光枪框架：输入、边框、站点推进、敌人行为库、Boss、HUD、过场播放、校准、存档。每款游戏主要产出关卡数据、素材和剧本；游戏特有的规则写在这款游戏自己的脚本里（见第 5.2 节）。“第二款不改框架”是要验证的复用目标，不是前提。框架的通用能力从首款的第一个站点和第一个 Boss 原型里提取，不提前发明完整的规则语言；公共框架里不允许出现按游戏 ID 判断的分支。
2. **设定是唯一依据。** 每款游戏有自己的设定目录 `games/<game_id>/bible/`：`world.md`（世界观）、`style.md`（美术风格）和 `style_refs/`（锚点图库）。它们是这款游戏所有 AI 环节提示词的来源，改设定可以整批重新生成，但不会影响别的游戏。首款的这些文件由 [GAME01_PAPER_LANTERN_CITY.md](GAME01_PAPER_LANTERN_CITY.md) 拆出来。
3. **每个生成物都可追溯。** 记录提示词、模型、版本、种子、参考图、费用、审核状态。缓存键的组成见第 6.7 节，相同输入不重复花钱。
4. **光枪约束写成规则，机器先验收，人后验收。** 关卡和画面先过规则校验、机器人试玩和追踪合规测试，过了才给你看。

## 3. 枪与游戏的接口契约

### 3.1 现有协议（以代码为准）

手机在 UDP 事件模式（`eventMode = udp`）下：

| 内容 | 行为 |
|---|---|
| 准星 | 文本 `x,y`，约 120Hz，发到游戏端口（默认 9000）。只在锁定有效时才发（`aimValid()`：等级不是 DEAD，包括只靠陀螺的 GYRO，最长 3 秒）。坐标**不限制在屏幕范围内**，枪口指向屏幕外时会发出界坐标。游戏端 0.6 秒没收到坐标应隐藏准星 |
| 射击 | 文本 `SHOT`，**不带坐标**。游戏用最近收到的准星坐标判定命中。DEAD 状态下点扳机不发 `SHOT` |
| 其他事件 | `RELOAD`、`COIN`、`START`、`EXIT`，ASCII 文本，无应答 |
| 发现 | 手机广播 `TVGUN_DISCOVER` 到 UDP 8001，PC 回 `TVGUN_HERE <端口>`。**游戏框架必须自己实现这个应答**，否则手机只能用保存的地址 |
| 坐标系 | 1920×1080 规范坐标，四角是白边**外缘** |

### 3.2 坐标系、单位和变换链

**评审发现的问题：** 追踪器的约定是“规范坐标四角 = 白边外缘”。但 `run_tv.py` 的 `norm_to_px` 把 (0,0) 映射到 `m + 24`。而它画白边用的 `cv2.rectangle` 线宽是以线为中心的，白边实际占 `m-12` 到 `m+11`。两边相差约 36 个窗口像素，缩放比例也不同。这可能是交接文档里“固定瞄点偏差”的一部分来源。

**三套坐标，单位分开写：**

| 坐标系 | 范围 | 单位写法 | 用途 |
|---|---|---|---|
| 相机图像坐标 | 640×360 | 相机像素 | 追踪器内部 |
| 规范坐标 | (0,0)–(1920,1080) 是白边外缘 | 规范像素 | 手机发出的瞄点；白边、暗区、命中半径、安全边距、离屏判定 |
| 窗口坐标 | 实际窗口分辨率 | 窗口像素 | 只在 `ScreenFrame` 内部使用 |

外黑边在规范坐标的范围之外，所以窗口像素和规范像素一般不相等，比例随显示配置档、过扫描调整和分辨率变化。除外黑边比例外，本文所有尺寸都是**规范像素**。

**变换链：**

1. 相机图像 → 规范坐标：追踪器的单应 `H`（手机端）。反方向（把规范坐标里的取样点投到相机图像）用 `H` 的逆矩阵，和 `guntrack.py` 的 `_measure_edges` 投影四角的做法一样。
2. 规范坐标 → 校准后规范坐标：游戏内校准拟合的修正单应（游戏端，按显示配置档保存）。
3. 校准后规范坐标 → 内容坐标：减去白边和暗区宽度（默认各边 72 规范像素）。内容坐标和规范坐标 1:1，单位相同。
4. 绘制方向反过来：内容坐标 → 规范坐标 → 窗口坐标。`ScreenFrame` 负责规范坐标到窗口坐标的映射，白边按规范坐标从外缘向内画 24 规范像素。

**离屏和非内容区：**

- 校准后的瞄点落在规范范围 (0,0)–(1920,1080) 之外（包括外黑边），才算离屏。离屏时扣扳机就是换弹。
- 落在白边或暗区上（规范范围内、内容区外）：算一次没打中，消耗一发，不判命中，也不触发换弹。

**游戏内校准：** 依次射击屏幕上 5 个点（中心和四角），拟合修正单应并保存。另外再射 4 个不参与拟合的检查点，用它们的误差判断校准是否合格。

**验收：** 在两个显示配置档下各改一次边框参数，用同一组已知点检查绘制位置、射击位置和追踪器取样位置是否一致；40 规范像素的命中半径在两种配置下画出来的大小比例一致。

### 3.3 协议改动（手机端，改动很小）

| 编号 | 改动 | 理由 | 决定 |
|---|---|---|---|
| P1 | `SHOT` 改为 `SHOT x,y,n`，带上开枪瞬间的预测坐标（和屏幕准星同一预测量）和序号 | 消除坐标包和射击包走不同线程、先后顺序不确定带来的误差；也和 HTTP 模式行为一致 | 阶段 0 做。游戏端同时兼容不带坐标的旧格式 |
| P2 | 锁定有效时准星包为 `x,y,g,n`，`g` 取 1–4（GYRO 到 FULL）。**失锁时也要发**：变成 DEAD 的瞬间立即发 `LOST,n`，之后每 200ms 发一次，直到恢复锁定。`LOST` 包不带坐标 | 现在发送线程只在 `aimValid()` 为真时发包（`MainActivity.java` 约 958 行），只改格式的话 DEAD 永远到不了游戏，游戏只能靠超时猜，分不清失锁和断网 | 阶段 0 做。游戏端兼容旧的 `x,y` |
| P3 | 游戏回发 `HIT` / `HURT` 给手机，手机震动 | 补偿没有后坐力的手感 | 阶段 3 再做 |
| P4 | 包里带枪编号 | 双人用 | 暂不做 |
| P5 | 游戏把边框几何发给手机：`FRAME 白边宽,暗区宽`（规范像素），连上时发一次，改参数时再发，之后每 2 秒重发；手机收到前用默认值 24、48 | 第 4.2 节的取样位置依赖暗区宽度，暗区宽度又在游戏端可调；不告诉手机，改了边框手机仍会采到白边或游戏内容 | 阶段 0 做，和第 4.2 节的追踪器改动一起做 |

**序号和时效规则（P1、P2）：**

- `n` 是手机这次运行内递增的序号，准星包（含 `LOST`）和射击包共用一个计数。准星包的序号比已收到的最大准星序号小，就是迟到包，直接丢弃，这样迟到的坐标不会覆盖新的锁定状态。射击包自带坐标，不因为比后发的准星包晚到而丢弃，序号只用来去重。手机重启后序号从 0 开始；游戏连续 2 秒没收到任何包，或者序号突然变小很多，就当作新会话，清掉旧状态。
- 不比较手机和 PC 的时钟，时效只按 PC 收包时间算。
- 新格式下，游戏收到 `LOST` 立即隐藏准星、提示“请对准屏幕”，在恢复锁定之前不判任何命中。
- 旧格式（`x,y` 和不带坐标的 `SHOT`）只作兼容：游戏只在最近一个坐标包收到时间不超过 100ms 时，才用它判 `SHOT`，否则这一枪当作失锁处理；0.6 秒收不到坐标就隐藏准星。兼容模式区分不了失锁和断网。
- 验收要覆盖 FULL→GYRO→DEAD、断网、恢复、迟到坐标包、迟到射击包，不允许用失效坐标判命中。

## 4. 屏幕布局和亮度规范（光枪硬约束）

这一节是整个工作流最重要的约束。所有美术提示词、校验器和框架渲染都以它为准，写入 `specs/lightgun_rules.md`。

### 4.1 布局（从外到内）

| 层 | 默认值 | 来源 |
|---|---|---|
| 外黑边 | 窗口短边的百分比，按显示配置档，见下表。它在规范坐标范围之外 | `run_tv.py` 用短边 4%；给白边外侧提供暗背景，也防电视过扫描切边 |
| 白边 | 24 规范像素，纯白 | 追踪器设计值 |
| 内侧暗区 | 48 规范像素，纯黑（见 4.2） | 追踪器的“内侧暗度”检查 |
| 内容区 | 规范坐标 (72,72)–(1848,1008)，逻辑分辨率 1776×936（宽高比约 1.90），内容坐标和规范坐标 1:1 | 游戏画面在这里画 |

白边和暗区宽度改动后，内容区随之变化，并通过 P5 告诉手机（第 3.3 节）。

这些值都做成框架参数，按**显示配置档**保存。显示器和电视都要支持（D7），默认两个配置档：

| 配置档 | 外黑边 | 说明 |
|---|---|---|
| `monitor` | 短边 2% | 显示器不过扫描，外黑边主要给白边外侧提供暗背景 |
| `tv` | 短边 4%，可调 | 电视可能过扫描切边；首次使用时显示调整画面，用键盘把边框缩放到四角完整可见 |

每个配置档单独保存校准参数。手机端的预测提前量也不同（交接文档：电视约 90–130ms，显示器约 50–70ms），框架在切换配置档时提示去手机上调整。阶段 0 两种设备都要实测。

### 4.2 内侧暗区：评审发现的关键问题

追踪器每采纳一条边之前，都会在这条边的外缘往里 **10 个相机像素**处取样，取样点亮度的中位数必须低于 `low_thr - 25`，否则当作灯具或文字屏拒收（`guntrack.py` 第 617–631 行，`inside_off = 10`）。`low_thr = max(150, 0.75 × 画面 98 分位亮度)`，也就是取样点在相机里的灰度通常要低于 125–165。

10 个相机像素对应多少规范像素，取决于屏幕在相机里有多大。相机处理分辨率是 640×360，主摄水平视场约 68°：

| 场景 | 屏幕在相机里宽约 | 1 规范像素约等于 | 取样点离白边外缘 |
|---|---|---|---|
| 27 寸显示器，2.5 米 | 130 相机像素 | 0.07 相机像素 | 约 140 规范像素 |
| 55 寸电视，2.5 米 | 260 相机像素 | 0.14 相机像素 | 约 70 规范像素 |

（估算值，阶段 0 用实测录制确认。）

所以在常见距离下，取样点会落进游戏画面里。打鸭子能过，是因为它的整个游戏区是黑的；真正的游戏画面一亮，边就会被拒收。反过来，离得很近时白边在相机里可能超过 10 像素宽，取样点会落在白边上，同样被拒收。

**决定（D2）：改追踪器，游戏暗角兜底。**

- **追踪器改动：** 取样点不再用固定的 10 个相机像素，而是用 `H` 的逆矩阵把“暗区中线”（规范坐标里距白边外缘 白边宽 + 暗区宽 / 2，默认 48 规范像素，宽度由 P5 传来）投影到相机图像上再取样。这样取样点的目标位置是暗区中线，不再随屏幕远近变化。追踪器原本就有单应，改动只涉及取样位置的计算。
- **取样仍有误差：** 投影用的是预测单应，预测误差、屏幕倾斜和运动模糊都会让实际取样点偏离中线，所以暗区宽度要留余量，不能当成“一定落在暗区”。另外，失锁后重新捕捉走的是 `_acquire()` 里的中空校验（`guntrack.py` 约 1111 行），不经过这条取样逻辑：持续追踪不丢边，不代表冷启动和离屏回屏也能重新锁上，两者要分别验证（第 4.3 节、第 10 节）。
- **暗区宽度的下限：** 暗区在相机里至少要有约 3 个像素宽，才不会被白边的模糊光晕盖住。按上表中屏幕最小的情况（1 规范像素约 0.07 相机像素）算，需要约 43 规范像素，所以默认取 48 规范像素。如果用超广角镜头（视场约 92°），同样距离下屏幕更小（约 0.05），需要约 60 规范像素。暗区宽度是框架参数，阶段 0 按实际使用的镜头和距离定。
- **两份实现同步改：** `scripts/guntrack.py` 和 `Tracker.java` 必须逐语句一致（交接文档的要求），改完跑 `run_track_replay.py` 和 `ReplayTest`，用 `test_res/` 里的全部现行录制做回归，可用率和抖动不能变差。现有录制的游戏区本来就是黑的，回归只能证明“没改坏”；“亮画面下不丢边”要靠阶段 0 新录的亮画面录制来证明。
- **游戏端：** 白边内侧画一条 48 规范像素的纯黑暗区。内容区四周再加一圈可调的**追踪兜底暗角**，默认关闭，只有实测仍丢边时才打开。它和风格包里的**美术暗角**（第 6.6 节，比如《纸灯城》的灯箱木框阴影）是两个独立参数：美术暗角属于画面风格，默认按风格包开启；兜底暗角只为追踪服务。

### 4.3 亮度上限

- 失锁重新捕捉时，追踪器要求白边内缩 18% 的区域里，超过 `low_thr` 的亮像素不能多于 30%（中空校验）。
- 追踪器的阈值是按整幅相机画面最亮的 2% 自适应的，画面里有和白边一样亮的大块内容，就会干扰边的检测。

框架的处理：在内容区最后一道后处理里加**亮度上限**，让内容区的任何像素都明显暗于白边。这条规则让美术不需要逐张检查亮度，但意味着：

- 不能有全屏白闪，包括传统光枪游戏的开枪闪屏。
- 爆炸、天空、雪地这类高亮内容会被压暗。**偏暗、高对比的美术风格最合适。**

**测量口径：** 上限按 sRGB 编码值的亮度 Y′（Rec.601 加权：0.299R + 0.587G + 0.114B）实现，初始值是白边的 75%。这只是渲染端好算的量，不等于线性光亮度，也不等于相机读到的灰度。例如 `#B8C4D6` 的 Y′ 约为白色的 76%，线性相对亮度只有约 55%。真正的约束是相机灰度，所以 75% 是**待标定参数**：阶段 0 在显示器和电视上分别建立“Y′ 上限 → 相机灰度 → 追踪表现”的对应关系，结果存进显示配置档。

**适用范围：** 亮度上限作用于内容区的所有层，包括字幕、HUD、过场和特效。白边和暗区在亮度上限和风格后处理**之后**单独合成，白边必须保持纯白，不能被风格后处理一起压暗。

### 4.4 准星和命中

每个目标由若干**命中区**组成，命中区跟着素材的可见部分走，类型如下：

| 类型 | 例子 | 被打中 |
|---|---|---|
| 主可伤害区 | 墨怪的墨身、居民身上的墨团、Boss 当前该打的部位、可射击的灯和招牌 | 造成伤害或触发机关；正常射击就能完成机制 |
| 弱点 | 朱砂印迹，完全落在主可伤害区里面 | 额外伤害或加分；永远不能是唯一的解法 |
| 保护区 | 人质和纸居民的身体 | 误伤惩罚 |
| 无效区 | 硬化状态的敌人身体、护盾 | 不伤害，给“打不动”的反馈 |
| 遮挡区 | 近景掩体的可见部分 | 子弹被挡住 |

**裁决顺序（每一枪）：**

1. 用校准后的瞄点（精确点）查所有命中区，取层级最靠前的那个。落在遮挡区就是打在掩体上，结束。
2. 精确点落在弱点上，按主可伤害区命中再加弱点奖励；落在主可伤害区、保护区或无效区，就按这个区处理，结束。
3. 精确点没落在任何区，才考虑吸附：15 规范像素内**只有一个主可伤害区**，且精确点和它之间没有保护区和遮挡区，才判为命中这个区（吸附命中不给弱点奖励）。保护区不吸附，也不放大：只有精确点打在纸身的可见像素上才算误伤。
4. 都不满足，就是没打中。

**尺寸：** 主可伤害区的有效半径至少 40 规范像素（是半径，不是直径）。有效半径的算法：先对区域做半径 12 的形态学开运算，去掉细尾巴、拉丝、飞白碎块，再把剩下的面积换算成等面积圆的半径。弱点在主可伤害区里面，可以更小。这个尺寸优先靠美术保证，也就是可射的部分本身要画得够大、边界看得清；不能用看不见的超大碰撞区来补。小目标需要放大命中区时，放大后的区域不能和任何保护区重叠，规则校验器负责检查。完全被掩体挡住的目标不能被吸附击中。

**状态切换：** 人质被救下的那一帧，它所有的命中区立即失效，连射的后几发不会再算误伤。

**最小测试：** 一名人质加一个相邻敌人，玩家要能说清每次命中或误伤的原因；纸身外面的空白处不会罚分。

- 准星默认显示（小号、半透明），可在设置里关掉（D3）。
- 开枪的视听反馈全部在 PC 端：枪声、命中火花或血花、命中标记。

## 5. 游戏设计规范

### 5.1 结构

| 层级 | 规格（首款） |
|---|---|
| 游戏 | 3 关，流程目标 15–20 分钟 |
| 关 | 4–6 个站点，最后接 Boss，每关游玩 3–5 分钟（含站点转场和 Boss，不含关头过场） |
| 站点 | 1 张背景 + 若干掩体槽位 + 若干波次 |
| 站点之间 | 3–5 秒**转场演出**，在引擎里做（第 8 节）；视频只用于个别特例 |
| 过场 | 开场 60–90 秒，每关开头 20–30 秒，结局约 60 秒，合计约 3–4 分钟 |

**时长口径：** 流程时长 = 三关游玩时长 + 全部过场，按“熟练玩家、不续关、不跳过过场”估算，不含教学失败重来和续关。它是设计目标，不是所有玩法下的保证。

**人数：** 首版单枪，朋友之间轮流玩。双人（P4）以后再定。

### 5.2 敌人行为原语

关卡数据只能组合下面这些原语。新原语要先进框架，再被关卡使用。

| 原语 | 说明 |
|---|---|
| `popup` | 从掩体左、右或上方探出，预警，攻击，缩回 |
| `run_across` | 横穿画面，途中可停下攻击 |
| `approach` | 从远处走近，越近越大，近身攻击（House of the Dead 式） |
| `thrown` | 投掷物或飞弹，可以在空中打掉 |
| `swoop` | 飞行敌人俯冲 |
| `hostage` | 人质或平民，误伤默认扣分扣血；单款游戏可以覆盖默认值（例如只扣分），在游戏设定里写明 |
| `pickup` | 道具箱，打中掉弹药、血或分数 |
| `boss` | 多阶段，可见弱点，阶段之间有转场动画 |

每个敌人都有：血量、命中区（第 4.4 节）、预警时长、攻击伤害、受击反应、死亡表现、分值。

**原语之外的通用能力。** 只靠上面的移动和攻击原语，表达不了首款的点灯、墨线连锁、净墨救人和笔顺。框架另外提供四类通用能力，关卡数据用它们把规则连起来：

| 能力 | 内容 | 首款用在哪里 |
|---|---|---|
| 命中区 | 一个目标挂多个命中区，每个区有类型（第 4.4 节）和自己的效果 | 净墨救人：墨团是可伤害区，纸身是保护区 |
| 状态 | 敌人和场景物件的状态机，状态决定命中区类型和可用的攻击 | 点灯：硬化 / 可伤害；人质：附身 / 获救 |
| 事件 | 命中、死亡、状态变化、计时到点等事件，可以被别的对象监听 | 点灯：灯亮起，通知所在区域的墨怪变软 |
| 目标组 | 把多个对象编成组，支持依赖、传播和顺序 | 墨线连锁：墨源死亡沿组传播；笔顺：只接受当前这一笔 |

这几类能力**从首款第一个站点和第一个 Boss 原型的真实需求里提取**，不提前设计完整的规则语言。数据表达不了的规则，写成这款游戏 `games/<game_id>/scripts/` 里的脚本，由关卡数据引用；公共框架里不写游戏 ID 判断。验收：用一份实际关卡数据完整表达“点灯 → 区域可伤害 → 净墨救人”，并能说清每个字段由哪个模块执行。

### 5.3 玩家规则（D4 已定）

| 项 | 默认 |
|---|---|
| 生命 | 5 |
| 弹匣 | 6 发。两种换弹都支持：枪口移出屏幕扣扳机（传统光枪做法，靠 GYRO 状态下的出界坐标，离屏的定义见第 3.2 节），或按手机“换弹”键。空弹匣扣扳机时屏幕提示 |
| 射击和换弹参数 | 最短射击间隔 0.15 秒；换弹 0.5 秒；回屏重新锁定的时间按阶段 0 实测（初值 0.5 秒）。三项都是框架参数，公平性检查要用（第 5.4 节） |
| 续关 | `COIN` 无限续关，分数清零 |
| 时间限制 | 不做 |
| 计分 | 击杀分 + 爆头 + 命中率 + 速度奖励，每关结算 |
| 难度 | 简单 / 普通 / 困难，只调预警时长、伤害、敌人血量和同屏数量 |

**运行状态（默认值）：**

| 情况 | 处理 |
|---|---|
| 暂停 | 游玩中按 `START` 或键盘 Esc 暂停；暂停时敌人、计时、动画全部停住 |
| 失锁 | 收到 `LOST` 后提示“请对准屏幕”，敌人照常行动（传统光枪做法）；连续失锁超过 2 秒自动暂停，重新锁定后倒数 1 秒继续 |
| 死亡和续关 | 生命归零进入续关倒数；投币后从**当前波次开头**重来，弹匣补满 |
| 站点转场 | 转场期间收到的 `SHOT` 丢弃，不耗弹、不计命中率 |
| 跳过过场 | 用来跳过过场的那一枪被跳过动作消费掉，不带进游戏 |

### 5.4 公平性数值（规则校验器检查）

| 规则 | 普通难度默认值 |
|---|---|
| 预警时长 | 至少 0.6 秒，困难至少 0.45 秒；预警必须同时有画面和声音 |
| 同屏同时预警 | 最多 3 个 |
| 目标最小尺寸 | 主可伤害区有效半径至少 40 规范像素（第 4.4 节） |
| 目标位置 | 不得进入内容区四边 60 规范像素以内 |
| 不可避免伤害 | 不允许：任何伤害都必须有足够时间提前击毙来源（按下面的动作成本检查） |
| 换弹窗口 | 每波之间至少有 1 秒没有威胁 |

上面几条都是局部条件，单独满足不能证明伤害躲得掉：三个敌人各自合规，叠在一起仍可能来不及处理。所以校验器还要检查**动作成本**：

- 对每一次会造成伤害的攻击，从这个威胁可见的时刻算起，求玩家处理掉同一时间窗口里所有威胁所需的最短动作序列：反应（按普通档机器人上限 0.4 秒）、每换一个目标的转移瞄准（0.25 秒）、每个目标需要的射击次数乘以最短射击间隔、弹药不够时的换弹和回屏、需要先点灯时打灯的那一发和灯生效的时间。这个总时长必须短于攻击落下的时刻。
- 弹药状态要带进计算：剩一发、需要点灯、同时有多个目标，是必查的边界情况。打灯、打掩体、打空都消耗弹药。
- 硬化状态的敌人，只有在玩家当时有可执行的解法时（让它变软的灯可见、可射，变软的时长够把它打死），才允许发动攻击。
- 校验器用固定随机种子跑，覆盖“剩一发 + 需要点灯 + 多目标”“换弹回屏时敌人攻击”等边界场景。

## 6. 美术管线（2D，直接 GPT 出图）

美术是整个工作流里最重要的部分（你的要求）。第一版只做 2D，图片统一由内置 GPT 生成。下面以首款游戏《纸灯城》的风格为例，设定见 [GAME01_PAPER_LANTERN_CITY.md](GAME01_PAPER_LANTERN_CITY.md)。本节是通用管线的概要；《纸灯城》的效果图、风格规范、逐类制作步骤、检查点和输出格式见 [ART_PLAN_PAPER_LANTERN_CITY.md](ART_PLAN_PAPER_LANTERN_CITY.md)。

### 6.1 模型分工

2026-11-03 审核人指定图片直接用当前内置 GPT 工具：风格样图、背景、角色、物件、UI、独立标题字、透明素材及局部编辑走同一路径，不需要 API 密钥。

场景按白模逐层生成透明素材，角色生成零件图或逐件出图。GPT 不保证返回结构化图层、包围盒或关节数据；这些由本地管线和视觉核对产生。色板由提示词、锚点和 C04 检查控制，不使用其他供应商的专有参数。

参考图、透明度、输出尺寸与编辑保真由 T01 小样验证；工具未提供的模型、种子、任务 ID 记空。图片编辑先查看目标图，明确保留项。独立资产逐项生成，保留全部尝试记录。

**文字规则：** 背景不烘焙关键文字，标题与关卡名字用 GPT 单独出透明字形并审核；其他文字由引擎渲染。

复杂动作优先分件、程序动画和 GPT 关键姿势。外部生成视频是单独启用的备选，不作为出图开工前置。详见美术方案 §0.1。

### 6.2 风格锚定（审核点 1）

1. AI 按风格、色板和年代物件要求，直接用内置 GPT 出约 30 张风格样图，涵盖站点、居民、墨怪与 UI，逐项记录调用。
2. 你从中挑 6–12 张，组成**锚点图库**。
3. 锚点图库是素材库，不是每次都全带：每次生成按用途从库里挑一个子集作为参考（站点挑站点类，角色挑角色类），优先选 1–3 张相关锚点，给白模留位置；实际输入能力由 T01 验证，不沿用旧供应商上限。
4. 风格漂移明显时，再考虑用已审核素材训练 LoRA。

### 6.3 站点背景

1. 按关卡列表生成整张站点图，宽高比 2:1，按纸雕灯的分层结构描述（近处深色剪影、中景台口、远处透光层）。
2. 用 GPT 按白模逐层生成或提取并补全透明 PNG，本地标注层级、包围盒并核对遮挡；近景层作为掩体。
3. 视觉模型标出敌人出现的槽位（纸层之间的空隙、招牌后面、窗户里），并估计每个槽位的敌人缩放。
4. 被前景挡住的部分，用 GPT 透明图像编辑补全，保证图层滑动时不露洞。
5. 输出 `station.json`：图层文件、层级、视差系数、槽位坐标和缩放、可射击物件（灯、招牌）的位置。
6. 引擎里每层随“灯光呼吸”轻微漂移，产生纸雕灯的深度感。

### 6.4 纸居民（分件纸偶）

1. 生成设定图：中性姿势，四肢和躯干分开，关节圆形搭接，钉铜色纸扣。
2. 拆件：首选让 GPT 直接生成透明“零件图”（所有部件在一张纯色底上分开摆放），再按连通区域切开；备选是参考设定图逐件生成透明部件。阶段 0A 两种都试，选成功率高的。
3. 视觉模型标出每个部件的轴心和关节点，套用框架里的人形纸偶模板（头、躯干、上臂、前臂、大腿、小腿）。同时标出纸身区域（保护区）和墨团位置（可伤害区），命中区随部件一起运动。
4. 动作全部由框架的程序化动作库完成：探出、走、受惊、挥手、被附身挣扎、获救弹跳、扔东西。AI 不画动作帧，所以同一个角色永远长一个样。

### 6.5 墨怪

1. 每种墨怪生成一张静态造型图（纯色底），BiRefNet 抠出来。墨是纯黑，和底色对比强，抠像很稳。
2. 框架里的墨着色器负责：噪声位移做蠕动、湿润高光、边缘飞白、滴落粒子、被光照中时的蒸发溶解。
3. 复杂动作优先分件和 GPT 关键姿势；墨舞龙使用分节绑定。外部生成视频只有单独启用后才作为备选。
4. 朱砂弱点是单独的一层，引擎用它做弱点奖励判定和高亮；墨身本身是主可伤害区（第 4.4 节）。

### 6.6 特效、UI 和字体

- 光束、命中光斑、墨花、墨烟都用着色器和粒子做，不生成视频，风格统一也省钱。全部受亮度上限约束。
- UI 框体、印章、标题毛笔字由图像模型生成；正文由引擎渲染，用思源宋体（开源授权）。
- 框架有一个统一后处理：纸张纤维颗粒、美术暗角（风格包参数，例如灯箱木框阴影）、灯光轻微闪烁，最后套亮度上限。追踪兜底暗角是另一个参数（第 4.2 节）。白边和暗区在这条后处理之后单独合成。

### 6.7 素材记录（manifest）和缓存

每个素材记录：ID、类型、提示词、参考图、模型和版本、参数、种子、费用、生成时间、审核状态（待审 / 通过 / 拒绝）、风格评分、追踪合规结果。

三样东西分开记：

| 概念 | 内容 |
|---|---|
| 请求指纹 | 缓存键。内置工具未暴露的型号/种子记 null，保留工具路由、提示词、引用和输出内容哈希。对这些内容一起做哈希：提示词、每张参考图的**内容**哈希（不是文件名）、实际调用的模型 ID 和版本、全部参数、管线版本（拆件规则、后处理脚本的版本）、上游素材 ID |
| 生成尝试 | 同一个指纹的第几次生成。被拒绝后重新生成时尝试编号加一，不会一直从缓存里拿到同一张废片。记录供应商任务 ID、费用和结果 |
| 已审核产物 | 审核通过的那次尝试的输出，进 Git |

构建只读取冻结的已审核 manifest，不访问缓存，换机器或清掉缓存也能从已审核素材重建。锚点图或风格设定更新后，依赖它们的素材被标记为“受影响”，等你决定是否重出；旧版游戏照旧能用原来的素材构建。

### 6.8 素材可用性验收

拆出 6 个图层只能证明有 6 张图，不能证明它们拼得成一个能玩的站点。阶段 0A 和之后每个站点、角色都按下面这些项验收：

| 素材 | 检查项 |
|---|---|
| 站点 | 按最大视差位移和运镜幅度滑动图层，不露洞、不穿帮；遮挡关系符合玩法；每个敌人槽位有安全的出现区域；敌人从槽位探出时的最小可见面积达到命中区要求；透明边缘没有残留底色 |
| 纸居民 | 每个部件有轴心和关节点；关节转动时不错位、不露缝；纸身区域和墨团区域标注正确，并且跟着动画走；全部程序化动作都能播放 |
| 墨怪 | 朱砂弱点层和造型对齐；着色器形变后弱点仍在可见部分上 |
| 循环视频 | 首尾的速度和轮廓连续，循环点看不出跳变；弱点在每一帧都跟得上 |

验收方式是在 Godot 里用最远、最近和转场三种状态实际播放，确认碰撞和可见部分对应。

## 8. 故事和过场管线

首款的过场以**引擎内演出**为主：用游戏里已有的纸层素材做运镜，配旁白和字幕。这样角色和场景天然一致，不需要口型，几乎不花视频生成的钱。只有少数素材做不出来的镜头才生成视频。

1. **设定扩写（审核点 2）：** 从设定文档生成完整的故事大纲、角色表、敌人图鉴、关卡列表。
2. **剧本：** 每段过场写成镜头表：时长、用到的图层、运镜（平移、推拉、图层滑开、灯光变化）、旁白、音效提示。
3. **引擎内演出：** 镜头表编译成 Godot 的动画数据，由 `CutscenePlayer` 播放。缺的画面（例如开场的工作台）按同样的分层方式生成新素材。
4. **特殊镜头：** 默认使用 GPT 场景层和关键帧交引擎演出；确需外部生成视频时单独核实能力与预算后启用，不阻塞图片制作。
5. **旁白：** CosyVoice 生成，后期加风格化处理（首款是磁带底噪和轻微变速）。
6. **视频格式：** ffmpeg 输出 1080p 30fps 的 Ogg Theora（`.ogv`）。Godot 4.7 核心只支持这一种视频格式。
7. **播放：** 过场在内容区里播放，白边始终可见。字幕由引擎渲染。按 `START` 或开枪跳过。
8. **站点之间的转场：** 引擎里做纸层滑开、翻折、灯光切换，不生成视频。

## 9. Godot 框架

- Godot 4.7 stable（2026-06-18 发布），GDScript。渲染器（Forward+ 或 Compatibility）在阶段 0B 按实际画面效果和性能定。
- 全屏，关闭不必要的后处理延迟。手机端的预测提前量只能估计瞄准位置，不能消掉网络、渲染和显示的实际延迟，提前量过大还会放大急停时的偏差，所以性能要单独治理。

**性能预算：** 分层透明图、墨着色器、粒子、后处理和序列帧会叠加成本。比如一段 5 秒、30fps、1920×1080 的动画，每帧存完整 RGBA8 并全部常驻，像素数据约 1.16 GiB（未裁剪、未压缩的估算）。所以：

- 阶段 0 先定目标 PC 和目标帧率（默认 60fps），原型阶段就记录帧时间、纹理内存，以及“扣扳机到画面反馈”的端到端延迟。
- 定出单张贴图的尺寸上限，序列帧按包围盒裁剪、降采样，只在用到时加载。
- 开枪反馈（光斑、音效、命中标记）优先保证；昂贵的装饰效果都要有降级档。

| 模块 | 职责 |
|---|---|
| `GunInput` | UDP 9000 收坐标和事件；UDP 8001 回发现应答；向手机发 `FRAME`（P5）；校准修正；兼容 P1/P2 新旧格式，按序号丢弃迟到包、识别新会话（第 3.3 节）；出界坐标加扳机判为换弹；开发时用鼠标模拟枪 |
| `ScreenFrame` | 外黑边、白边、内侧暗区、内容区缩放、规范坐标和窗口坐标互相映射、亮度上限、显示配置档（`monitor` / `tv`）、电视过扫描调整画面 |
| `Calibration` | 5 点校准加 4 个检查点，按显示配置档分别保存修正参数 |
| `StationRunner` | 读关卡 JSON，按站点和波次调度，处理站点转场、暂停、续关恢复点（第 5.3 节） |
| `EnemyLib` / `BossLib` | 第 5.2 节的行为原语，以及命中区、状态、事件、目标组四类通用能力；加载游戏自己的规则脚本 |
| `HitResolver` | 按第 4.4 节的顺序裁决每一枪 |
| `Hud` | 生命、弹药、分数、换弹提示、失锁提示 |
| `CutscenePlayer` | 按镜头表演出引擎内过场；播放 `.ogv`；引擎字幕；跳过 |
| `CutoutPuppet` | 分件角色的关节模板和程序化动作库（2D 分件动画是通用能力，不限于纸偶） |
| `StylePack` | 加载每款游戏自己的“风格包”：着色器、后处理、命中特效。首款的风格包是墨着色器（蠕动、湿润高光、飞白、滴落、蒸发溶解）和光束、墨花粒子，放在 `games/g01/style/` |
| `AudioBus` | 音效、音乐、语音分组 |
| `DebugState` | 只在调试构建开启：本机端口输出实时游戏状态，给机器人和测试用 |
| `Save` | 设置、校准参数、最高分 |

**AI 怎么操作 Godot：** 内容都是数据，AI 平时只改 YAML 和素材；改框架代码时用 Godot MCP。首选 [satelliteoflove/godot-mcp](https://github.com/satelliteoflove/godot-mcp)（能冻结游戏时钟、单步、注入输入、读运行时状态，适合 AI 自测）；需要大量编辑器操作时再加 [godot-ai](https://github.com/hi-godot/godot-ai)。MCP 能在本机执行任意代码，只监听本机。

**关卡格式：** 写 YAML（AI 和人都好读），构建时按 `level.schema.json` 校验并编译成 JSON 给 Godot 读，省掉 Godot 里的 YAML 插件。

## 10. 自动验收

| 层 | 内容 | 不过时 |
|---|---|---|
| L0 结构 | 关卡 YAML 过 schema | 退回关卡设计 |
| L1 规则 | 第 5.4 节的公平性数值和动作成本检查 | 退回关卡设计 |
| L2 试玩 | 虚拟光枪机器人按真实 UDP 协议往 9000 发坐标和事件，从 `DebugState` 读目标状态 | 自动调关卡参数 |
| L3 追踪合规（筛查） | 游戏截图按随机单应投影成 640×360 模拟相机画面，加模糊、噪声和曝光变化，喂给 `guntrack.py`，检查边是否被拒收、中空校验能否通过 | 退回美术或调亮度参数 |
| L3 追踪合规（实录） | 真机连续录制，见下文 | 退回美术、调亮度参数或改追踪器 |
| L3 风格 | 视觉模型对照锚点图给素材打分；分数不够就重生成，同一素材最多自动重试 2 次，之后交给你看 | 重新生成 |
| L4 人工 | 你试玩 | 你给意见，AI 改 |

**机器人的瞄准模型**用 `test_res/` 里的真实录制标定：抖动、甩枪拖尾、固定偏差。另加反应时间 250–400ms 和偶尔失手。分三档水平各跑多次。机器人做决策只能用玩家看得见、认得出的目标状态（`DebugState` 给每个目标标可见性）；被掩体挡住或藏在暗处的敌人的真实坐标只用于诊断报告，不能拿来瞄准。

**试玩指标（默认目标，可调）：** 普通水平机器人第 1 关通关率 70–90%，第 3 关 40–60%；不存在任何水平都躲不掉的伤害；弹药耗尽导致受伤的次数每关不超过 2 次。通关率按**不使用续关**统计，续关次数另外记录。

**追踪实录：** 截图筛查只能当快速检查，最终以真机连续录制为准。录制要覆盖冷启动、快速甩枪、离屏换弹、回屏、点灯、Boss 特效和过场，在显示器和电视上各录一套，并记录环境（距离、灯光、镜头）和参数，让失败片段能重复回放。指标除了 FULL / PARTIAL 的时间占比，还要记录最长一次连续失锁、重新锁定的耗时和错误锁定次数：平均 95% 的可用率区分不了“零散丢几帧”和“一次长时间没法操作”。

## 11. 编排

- **管线 CLI `gf`：** 每一步都可以重复执行；输入不变就直接用缓存。例如 `gf gen backgrounds --game g01 --stage 1`、`gf gen sfx --game g01`、`gf build --game g01`、`gf test --game g01`。
- **图像工具入口：** agent 直接调用内置 GPT 图像工具；本地 CLI 管理归档、元数据和检查。能力清单记录实际输出、透明度、参考与编辑测试，未知模型与费用字段不可伪造。外部 API 仅在明确启用后接入。
- **调用记录：** 内置图片工具调用前记录本地尝试 ID，返回后保存输出与结果标识；中断先核对现有结果，不能盲目重发。外部服务的任务 ID 和轮询仅对明确启用的服务适用。
- **内置出图用量：** 每批最多 10 次，0A 最多 120 次，按任务表和单素材重试上限管理；未披露费用记未知，不按旧供应商价格估算。
- **外部付费预算闸门（仅明确启用后）：** 单次运行上限 $20，单款游戏累计上限 $600（D9）。闸门比较的是“已结算 + 已提交未结算 + 本次最坏估算”，不是只看已结算，否则并发提交和失败重试会越过上限；会超出就停下来问你。失败但已计费的生成、没通过审核的生成都记进账本。manifest 按原币种记账，闸门按配置文件里写明的固定汇率折算成美元比较，汇率改动也记录下来。
- **Cursor Skills：** 每个环节一个 Skill，写明输入、输出、调用哪条 CLI、怎么自检。
- **审核画廊：** `gf review` 生成本地网页，你在网页上点“通过 / 拒绝 / 备注”，结果写回 manifest。
