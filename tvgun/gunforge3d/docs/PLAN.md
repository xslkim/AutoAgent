# GunForge3D：3D 光枪游戏引擎方案

版本：v0.4 · 2026-11-16 · 状态：三次评审修订（修订点见 §10），并补充了与美术阶段的衔接（§11），作为实现基线；玩法效果待实测。执行拆分见 [TASKS.md](TASKS.md)，开发机环境见 [DEV_ENVIRONMENT.md](DEV_ENVIRONMENT.md)。

## 1. 目标与已确认的边界

目标：启动 3D 光枪游戏引擎，用一个 3–5 分钟的白模关卡验证方向。关卡必须真的好玩到能下判断，不是技术演示。

沿用的产品边界与当前实现决策（2026-11-15）：

| 项 | 决定 |
|---|---|
| 与 2D 的关系 | 独立工程，位于本仓库 `gunforge3d/`。与 `gunforge/`（2D）互不引用代码。只有手机输入协议保持一致 |
| 引擎与语言 | 由方案决定：Godot 4.6.3 + GDScript，Forward+ 渲染（理由见 §2） |
| 镜头形态 | 轨道式：镜头沿预设路径自动前进，在战斗点停下清敌，部分路段边走边打 |
| 输入 | 首版只做 PC 鼠标。输入层按手机协议抽象，画面按 TVGun 布局带白边框、暗带并限亮，为后续 UDP 输入源保留统一接口 |
| 题材 | 有主题的白模：《仓库突入》。全部用几何体搭建，不做正式美术，不引入外部素材 |
| 玩法 | 单发手枪、弹匣换弹、生命、计分、续关、结算；弱点与部位判定；人质与误伤惩罚；拾取与可破坏物；多阶段 Boss |
| 防御 | 以攻代守：攻击前有预警，在预警窗口内击杀或打断敌人、击落投射物即可免伤。不需要额外按键 |
| 时长 | 3–5 分钟，共11段：6个移动/演出段、4个普通战斗段、1个Boss段 |
| 数据驱动 | 关卡全部由 JSON 描述（白模几何、轨道、敌人编排），带校验器、调试接口和机器人，Agent 可自动验证 |
| 声音与反馈 | 代码合成音效，完整打击反馈 |
| 执行 | Sonnet 在开发机按任务顺序执行，每个任务自测通过后提交到 `main`，不 push |

不在首版范围：手机 UDP 输入与校准、双人、正式美术与动画资源、存档、多关卡、可视化关卡审阅工具、Windows 导出包、踏板或掩体机制、按住连射。

`docs/FPSGAME_TVGUN_PLAN.md` 与 `D:\FPSGame` 不作为依据。

## 2. 技术选型

**Godot 4.6.3 + GDScript + Forward+。**

- 开发机已有 `D:\gunforge_cache\tools\godot-4.6.3\Godot_v4.6.3-stable_win64_console.exe`，不需要安装任何东西。
- 无头模式可跑逻辑测试，命令行可启动、截图、退出，适合 Agent 自测。已在开发机用临时工程验证。
- GDScript 不需要编译工具链，改完即跑，执行模型出错面小。
- 引擎免费开源，3D 能力对白模和街机光枪体量足够。
- Forward+ 的阴影和环境光让白模有体积感，开发机 RTX 5090 无压力。首版只验收Forward+。以后若切Compatibility，需另做环境光、阴影与特效降级验证，不承诺直接切换后画面等价。

已验证的两个关键假设：

1. 自算的相机射线（`basis * (ndc.x·tan(fov/2)·aspect, ndc.y·tan(fov/2), -1)`）与 `Camera3D.project_ray_normal` 的差值约 1e-7。命中判定可以完全不依赖引擎节点。
2. 非无头模式下，`SubViewport` 画面可用命令行保存为 PNG（1776×936）。

## 3. 总体结构

核心原则：**逻辑与表现分离，逻辑是唯一事实来源。**

```
输入源（鼠标 / 以后的手机 UDP / 回放 / 机器人）
        │  规范坐标 1920×1080，经 Router 转为内容坐标 + SHOT/RELOAD/START/COIN
        ▼
  Sim（纯逻辑，60Hz 固定步长，无节点，确定性）
   ├ 轨道相机、导演（出怪/波次/攻击令牌）
   ├ 角色行为、投射物、道具、拾取、人质
   ├ 射线命中（自写几何求交）、规则、计分、流程
   └ 每 tick 输出：状态 + 事件列表
        │
        ├──► View（Node3D 镜像：白模、角色、特效）
        ├──► HUD（2D：准星、预警圈、生命、弹药、字幕）
        └──► Audio（合成音效，按事件播放）

  Shell（窗口层）：黑底 + 白边框 + 暗带 + 限亮后的内容画面
  Dev（开发）：TCP 调试接口、回放、截图、机器人、关卡校验器
```

为什么命中不用 Godot 物理引擎：

- Sim 不依赖场景树，可在无头模式下以远超实时的速度跑完整关，机器人和回放才可行。
- 同一输入序列得到同一状态哈希，回归测试可靠。
- 命中形状只有球、胶囊、盒、圆柱四种，求交代码量小且可单测。

### 3.2 画面与坐标（与手机输入一致的基础）

沿用 TVGun 的规范坐标，数值与 2D 工程的 `screen_frame.gd` 相同，但代码独立重写：

- 规范空间 1920×1080，四角是白边框外缘。
- 白边 24，内侧暗带 48。内容区为规范坐标 `[72,72]–[1848,1008]`，即 1776×936。
- 窗口内等比放置规范框，四周留外黑边（显示器档 2.2%，电视档 4.5%）。
- 3D 相机的宽高比固定为 1776:936，垂直视场默认 60°。
- 3D 与 HUD 一起渲染到固定1776×936的内容 `SubViewport`，由 Shell 等比缩放显示，经限亮着色器（sRGB Y′ 上限 0.75，可配置）后贴到内容区。白边框在其上方单独绘制，任何特效都盖不住它。

输入事件统一为：

| 事件 | 字段 | 鼠标映射 |
|---|---|---|
| AIM | x, y（规范坐标）, valid | 鼠标移动。只用于显示准星，不进入 Sim |
| SHOT | x, y | 左键 |
| RELOAD | — | 右键或 R |
| START | — | Enter |
| COIN | — | 5 |
| EXIT | — | Esc（Shell 处理为暂停） |

规则与 2D 一致：SHOT 落在规范框之外等于换弹；落在白边或暗带内照常扣弹但不命中。菜单和结算不用可点击控件，全部用 SHOT 或 START 操作，手机接入后无需改界面。

以后新增 `udp_source.gd` 产出同样的事件；坐标契约不变，但真实手机仍需验证丢包、校准和目标尺寸，不视为首版已经验收。预留 `calibration`（Transform2D）和 `assist_px`（命中宽容半径）两个配置，首版分别为单位变换和 0。

### 3.3 Sim 的确定性

- 固定 60Hz。时间一律用 tick 计数，关卡 JSON 里的秒在加载时换算为 tick。
- 随机数只用 Sim 自带的、由关卡 `seed` 初始化的 `RandomNumberGenerator`。
- Sim 的输入只有带入口 tick 的 SHOT/RELOAD/START/COIN；SHOT 已转换为内容坐标并携带 in_content。每 tick 先处理输入命中，再更新相机/行为/投射物，最后判断段落和阶段切换；预警最后一 tick 被击杀的敌人不会伤害玩家。完整顺序及计时边界见 TASKS T03。
- `snapshot()` 包含全部可影响后续玩法的状态及段入口检查点（不递归），排除 events、Shell 和表现状态；实体按稳定序号排序，rng 的64位 seed/state 转十进制字符串。`state_hash()` 用 `JSON.stringify(snapshot(), "", true, true).sha256_text()`，显式启用键排序和完整浮点精度。
- 回放记录引擎构建、模拟代码哈希、关卡/规则/原型哈希、带 tick 的输入序列及摘要、final_tick 和最终状态哈希。只保证同一 Godot 4.6.3 Windows 构建和相同模拟代码/数据内复现。跳段或启用调试控制的会话不生成标准回放；窗口回放隔离现场玩法输入。
- Camera3D 与可命中的部件始终镜像 Sim，不添加独立相机震动、俯仰或活体顿帧。受伤震动仅作用于非瞄准装饰（≤6内容像素、0.15秒）；顿帧和慢镜头仅作用于已不可命中的残骸、粒子。

## 4. 玩法设计

### 4.1 核心循环

镜头带玩家前进，敌人从掩体后、门口、高处出现。每个敌人攻击前有一段连续可见的预警（收缩的圆环加提示音）。玩家在预警结束前击杀或打断它，否则掉一格生命。弹匣有限，换弹有时间成本。打头一枪毙命且高分，连续命中累积连击。人质不能打，油桶可以利用。

### 4.2 玩家规则（`data/rules.json`，初值，T20 调参）

| 项 | 初值 |
|---|---|
| 生命 | 5，上限 5 |
| 弹匣 | 8 发，备弹无限 |
| 换弹 | 0.8 秒，期间不能开枪；弹匣空时开枪只有空响并闪烁换弹提示 |
| 射击间隔 | 最短 0.1 秒 |
| 受伤无敌 | 1.0 秒 |
| 续关 | 死亡后10秒内 START 或 SHOT 续关：满生命满弹匣，从段入口检查点重开；本段分数/道具/人质结果回退，carry敌人恢复，累计受伤/耗时/命中统计和续关次数不回退。免费模式，不扣币；COIN只计数 |

### 4.3 攻击令牌（公平性的核心）

每个段有 `tokens`（默认2）。普通敌人拿到令牌才能预警；攻击结算、打断、死亡或逃跑即幂等释放，释放后冷却0.6秒才能复用。投掷时把所有权转交给投射物，击落/命中/清除才释放，投掷者随后死亡不重复释放。换段清理旧威胁，carry敌人重新申请新段令牌。降令牌上限时先等待已有占用释放，不强行中断攻击。Boss自带节奏，不占令牌，小怪仍受限制。

预警必须对应实际可伤害且可见的部件。失去可见性时重置完整预警，恢复后重新计时，不累积零碎窗口；连续4秒不可见取消攻击并释放令牌。HUD读取Sim剩余tick，见TASKS T10。

### 4.4 敌人与对象

所有人形共用一套几何体骨架（头球、躯干盒、四肢胶囊），姿态由 `pose_lib` 的纯函数给出。Sim命中与View渲染用同一份部件变换。命中结果保留实体id、part和zone，伤害逻辑不得根据位置猜部件；共享几何、相机一致性及实际屏幕投影命中均需测试。

| 类型 | 行为 | 生命与部位 | 预警 |
|---|---|---|---|
| 射手 gunner | 进场到位，蹲在掩体后，周期性探身瞄准开枪 | 身体 2 枪，头 1 枪 | 1.6 秒。命中任意部位打断并硬直 0.4 秒 |
| 冲锋兵 rusher | 沿路径跑向镜头，贴近后挥砍，之后每 1.5 秒一次 | 身体 3 枪，头 1 枪 | 0.7 秒。命中使其减速 |
| 投掷兵 thrower | 站位投出抛物线投射物，飞行 1.6 秒 | 身体 2 枪，头 1 枪 | 抬手 1.0 秒，投射物飞行中可击落 |
| 盾兵 shield | 持盾缓步逼近，放下盾攻击时暴露 | 盾无效，腿可打，头 1 枪 | 1.2 秒，此时躯干与头暴露 |
| 人质 hostage | 蹲伏、横穿或被挟持；held姿态降低头部0.30米、手臂不举高，头部中心射线需实测无遮挡 | 打中扣 1 生命、扣 500 分 | 段内存活或挟持者被杀即获救：+500 分，+1 生命 |
| 油桶 barrel | 1 枪引爆，半径 3.5 米内敌人受 5 点伤害，人质同样会死 | — | — |
| 补给箱 crate | 2 枪击碎，掉出拾取物 | — | — |
| 拾取物 pickup | 医疗包 +1 生命，奖章 +300 分。射击收集，6 秒后消失 | — | — |

### 4.5 Boss：重装机甲

装卸区尽头的大型机甲，约 70 秒。

- **阶段 1**：机体全身装甲。两肩导弹舱是弱点（各 6 枪）。每 4 秒齐射 2 枚导弹，飞行 2.2 秒，可击落。两舱全毁进入阶段 2。
- **阶段 2**：胸口核心（共 28 点）在主炮蓄力时打开。蓄力 2.5 秒内命中核心 5 枪可打断，机甲瘫痪 2 秒且核心继续暴露；否则玩家掉 1 生命。两次蓄力之间放出 2 个冲锋兵。
- **阶段3**：核心剩余≤11点时仅进入一次，终止旧状态和残留小怪；机甲前压，交替3枚导弹与2.0秒蓄力（需6枪打断）。成功打断后核心继续开放2秒，失败扣血；随后关盖并进入下一循环。
- 击毁后设置 boss_defeated，清除全部威胁，残骸连环爆炸后进入收尾。150秒超时则判任务失败，直接结算且不发击毁/通关奖励，不播放“任务完成”。
- 机器人需按阶段选择存活导弹舱或已打开核心，复用原档位反应/瞄准/抖动；不能套人形头/躯干选择规则。

### 4.6 计分与结算

- 普通敌人身体命中20、弱点命中50、击杀100、弱点击杀另加100，击落投射物50。Boss弱点每枪50；击毁导弹舱500、Boss3000为固定奖励，不叠加普通敌人击杀/爆头分。
- 连击：命中有效敌人部件、投射物、道具或拾取物先+1，再以 `1 + min(连击,20) ×0.05` 乘本次命中/击杀分，合并后向下取整；奖励不乘倍率。打空、装甲、世界、受伤和误伤人质清零。爆炸按稳定实体顺序逐个计普通击杀分及连击；不重复增加 shots_hit。
- 段成功清场且所有尝试累计无伤+500，超时不给。通关结算奖励为 `roundi(命中率×2000) + 剩余生命×300`，命中率取0–1，零发射击记0；每发最多计一次有效命中。
- 续关回滚当前段的得分账本和道具/人质状态，保留段入口carry敌人，避免靠重打刷分或删除敌人降低难度。累计运行指标包含失败尝试，不因回血/续关抵消。普通段超时可继续路线，但不计入标准验收通过；Boss必须击毁才能cleared。
- 评级 S/A/B/C 按关卡 `par_score` 的百分比，结算显示得分、命中率、弱点率、获救人质、受伤次数、续关次数、用时。

### 4.7 反馈

- 视觉：枪口闪光、弹道线、世界弹孔与碎屑、敌人受击闪白、弱点命中的醒目火花、装甲弹开的火星、死亡倒地并淡出、爆炸、飘分、命中标记、受伤红色暗角、非瞄准装饰轻震、Boss残骸慢镜头。
- 预警：HUD 在敌人身上画收缩圆环，黄变红，最后 0.3 秒闪烁。投射物上有跟随的红色菱形及到期威胁提示。投射物到期按街机计时造成伤害，不另作与移动相机的接触判定；换段时清除。
- 声音：全部代码合成。枪声、空仓、换弹、身体命中、弱点命中、装甲、预警提示、受伤、爆炸、拾取、人质、Boss 警报、界面，另有一条简单的紧张脉冲循环作为背景。

## 5. 关卡《仓库突入》

坐标：+X 向右，+Y 向上，玩家朝 −Z 推进，单位米，眼高 1.6。

| 段 | 类型 | 时长 | 内容 | 验证点 |
|---|---|---|---|---|
| S0 巷口进场 | 移动 | 4 秒 | 镜头沿小巷前推，字幕提示操作 | 3D 纵深感 |
| S1 巷口 | 停留 | 约 30 秒 | 两波射手从垃圾箱和木箱后探身；一个油桶 | 掩体遮挡、爆头、换弹节奏 |
| S2 冲门 | 移动 | 8 秒 | 穿过卷帘门时 2 个冲锋兵迎面冲来 | 边走边打、近身压迫 |
| S3 装卸区 | 停留 | 约 35 秒 | 平台上的射手、高处走道的投掷兵、横穿的人质 | 高低差、击落投射物、克制开枪 |
| S4 货架通道 | 移动 | 15 秒 | 镜头左右摆，货架间依次闪出 3 个射手；补给箱含医疗包 | 运动中瞄准 |
| S5 通道尽头 | 停留 | 约 35 秒 | 镜头停在通道前段，2 个盾兵自尽头逼近，冲锋兵夹击，油桶 | 部位判定、目标优先级 |
| S6 上楼 | 移动 | 12 秒 | 走完通道余下部分，沿楼梯上夹层，镜头抬升，上方投掷兵 | 垂直运动 |
| S7 夹层办公室 | 停留 | 约 30 秒 | 被挟持的人质（只露挟持者的头），窗后射手 | 精确射击 |
| S8 下降 | 移动 | 7 秒 | 俯视装卸区，降到地面，Boss 登场 | 演出 |
| S9 Boss | 停留 | 约 70 秒 | 重装机甲三阶段 | 多阶段、弱点轮换 |
| S10 收尾 | 移动 | 3 秒 | 镜头拉远，结算 | — |

合计约249秒（移动/演出49秒，普通战斗130秒，Boss70秒）。移动时长按约88米推进距离和≤2.5米/秒平均速度分配；具体轨道须按弧长检查，不能依赖hold相机漂移补足距离。每个停留点前方必须留出战斗纵深（敌人站位5–11米）：S5因此停在通道前段而不是尽头，余下的通道并入S6。停留段的持续轻微漂移用轨道的 `drift` 字段表达，离段前自动回到基准姿态，不占用关键帧时间。具体坐标、数量和时间由执行者按 TASKS 的约束制作，并用校验器、机器人和截图调到达标。

## 6. Agent 可验证性

这是引擎而不只是游戏的原因，首版就要有：

1. **关卡校验器**：结构与引用、出生点不在实体内、战斗站位的弱点从该段相机可见且在安全区内、目标在屏幕上不小于最小像素、预警不短于下限、每个停留段有超时、总时长在范围内。
2. **调试接口**（TCP 127.0.0.1:19020，行分隔 JSON）：state、freeze、step、input、seek、capture、set、luma、quit。自动化启动的窗口（脚本、回放、性能采集）不因失焦而暂停。
3. **回放**：校验运行环境/数据/输入摘要后复现，按规范完整精度快照比较最终哈希；不同但效果等价的输入允许得到相同最终状态。
4. **机器人**：读 Sim 状态，按反应时间、瞄准时间、落点抖动三个参数模拟新手、普通、高手，无头跑完整关并输出每段的受伤、用时、命中率。它是可玩性的量化代理，不替代人工试玩。

最终指标以 TASKS T20 为唯一执行口径，每档固定种子1..10：average至少9次不续关通关，这些通过记录各自190–270秒、Boss50–90秒；10次平均受伤2–4、至少7次A/B。expert全部通关、平均受伤≤1.5、至少5次S；novice全部在续关≤2次内通关；idle全部在S3结束前首次死亡。被计为通过的运行均须Boss击毁、普通段无超时、攻击预警审计0违规。

“受伤”指每次实际扣生命（含误伤人质），回血不抵消；总用时只累计playing tick，包含失败尝试，排除暂停和续关倒计时。保留所有种子的原始结果，不能只统计成功记录的受伤。T18使用非Boss阶段的中间指标，T20才验完整关。

## 7. 风险

| 风险 | 应对 |
|---|---|
| 白模缺乏打击感，无法判断方向 | 反馈与音效列为必做任务（T14、T15），不作为可选项 |
| 头部目标在远处太小，以后手机精度不够 | 校验器限制最小屏幕尺寸；默认60°视场下人形战斗深度优先5–11米（r=0.17米的头在约11.48米处才有12内容像素半径）；预留 `assist_px` |
| 亮画面影响以后的白边追踪 | 首版就带白边、暗带和限亮；白模配色的亮度本来就低 |
| 机器人通过但人玩不好玩 | T10、T15提供早期试玩入口，T20输出完整清单，由用户判断；机器人只筛查明显数值问题，未收到试玩反馈不阻断独立开发 |
| 执行模型在大任务上跑偏 | 任务按依赖切小，每个任务有可运行的验收命令；逻辑先于表现；每任务一次提交 |

## 8. 方向判断标准

首版完成后，请用户用鼠标试玩并回答：

1. 轨道镜头的移动和停留节奏是否舒服，3D 纵深是否比 2D 定点更有临场感。
2. 预警、打断、击落投射物这套以攻代守是否紧张而公平。
3. 爆头、盾兵、挟持人质的部位判定是否有手感。
4. 4 分钟内有没有重复感，Boss 是否是高潮。
5. 关卡 JSON、校验器、机器人这条链是否足以让 Agent 继续做第二关。

## 10. v0.3 修订（2026-11-16）

只修正方案内部的矛盾和会卡住执行的缺口，产品范围不变：

- **关卡几何**：S5 原停在 z=−60，距通道尽头只有4米，放不下“自远处逼近的盾兵”、≥5米的深度差和距相机≥4米的油桶。停留点改到 z=−52，S6 相应延长为12秒，总时长约249秒。
- **停留段漂移**：原规则要求离段不早于最后一个相机关键帧，用关键帧做持续漂移会把停留段（含Boss战）拖到关键帧结束。改为独立的 `drift` 字段，离段前自动归零。
- **机器人与挟持人质**：人质保护半径（1.5σ）在常见距离上大于挟持者头部与人质头顶的间距，novice/average 会永远放弃挟持者并导致超时。改为先偏移瞄点，目标正在预警或没有其他目标时照常冒险开枪。
- **盾兵**：原盾下沿（0.43米）从相机高度看会挡住腿部中心（0.41米），瞄腿中心实际打在盾上。盾下沿抬到0.63米，机器人的遮挡检查纳入装甲部件。
- **校验器**：油桶近相机规则原本覆盖油桶存在的全部时段，镜头在后续移动段路过小巷油桶就会报错；改为只查油桶所属段。
- **自动化可靠性**：失焦自动暂停不作用于脚本/回放/性能运行；性能指标改为关闭 VSync 后的帧间隔分位数；数据与代码哈希先把换行归一为 LF；需要渲染的限亮测试明确为窗口模式自检，不进无头测试。
- **其他澄清**：实体 id 约定、安全框定义、空轨道与没有 required 敌人的停留段的行为、射击冷却测试移到有射击功能的 T08、HUD 不再二次缩放、调试端口可改。

## 11. 美术阶段衔接（2026-11-16）

本机工具路径、版本、验证范围和未具备条件见[DEV_ENVIRONMENT.md](DEV_ENVIRONMENT.md)。T00–T20仍是独立白模阶段：禁止引入外部素材/额外工具链的限制适用于该阶段。后续美术框架AF任务允许在gunforge3d/artkit下使用隔离Python环境和已有Blender；素材导入及EI/WR接入在T20完成且用户认可方向后执行，按两份ART3D文档验收。不提前改变白模验收标准。

纯表现资产覆盖原颜色，不删除或迁移archetypes里的字段。EI05启用姿态轨属于玩法改动：加载阶段校验并注入Sim（step期间不读文件），轨迹存game/data/poses；回放增加pose_data_sha256及姿态配置标识，快照包含clip/tick。修改轨迹必须拒绝旧回放并重新跑T20。--art开关仅控制View；同一玩法姿态配置开/关美术的最终哈希相同。

Compatibility属于后续EI06新增验收，Forward+白模性能结果不代表Compatibility性能。启动器必须把引擎参数`--rendering-method gl_compatibility`放在`--`之前，游戏参数放在之后；建议EI06新增`-Renderer forward_plus|gl_compatibility`并验证透传。框架与游戏文档若数值冲突，玩法尺寸以TASKS及已生成的Sim数据为准，美术不得擅改。

扩展空间（2026-11-16）：美术风格和硬件档位不是引擎的固定属性。白模阶段和首个美术档案之外，以后可以增加别的风格和更强的硬件档位，规则见[ART3D_FRAMEWORK.md](ART3D_FRAMEWORK.md) §18。对引擎侧的要求有四条：渲染器由启动参数选择，`-Renderer`的取值同时预留`mobile`；`--art`的取值是`off`、`on`或档案名，`on`等同于游戏的基准档案；灯光、环境、后期的设置按档案放在美术数据里，由View读取，Sim不读，同一玩法姿态配置下任何档案的最终哈希相同；任何后期效果都在内容视口内完成，限亮着色器和白边框仍在它们之后，白边框始终是画面里最亮的。这些要求在EI阶段落实，不改变T00–T20的白模验收，白模阶段不需要为此提前写代码。
