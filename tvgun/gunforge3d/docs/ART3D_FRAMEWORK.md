# 光枪游戏 3D 美术资产框架

版本：v0.1 · 2026-11-16 · 状态：方案，尚未实现，也未在开发机验证。

本文是通用部分：规则、数据契约、流水线和检查，与具体游戏无关。针对某个游戏的方案另写，第一份是 [ART3D_PLAN_WAREHOUSE_RAID.md](ART3D_PLAN_WAREHOUSE_RAID.md)。

## 1. 定位与分工

目标：让 AI 按固定流程自动制作光枪游戏的 3D 美术资产，人只在批次审核时参与。

| 层 | 产出 | 谁做 | 变化频率 |
|---|---|---|---|
| 框架（本文 + 工具 `artkit`） | 规则、数据格式、流水线、自动检查、模板 | 一次建好，按经验修订 | 低 |
| 游戏美术方案 + 任务文档 | 风格包、资产清单、每个资产的规格单、批次与任务 | 规划模型（高能力模型），依据游戏策划案和本文 | 每个游戏一次 |
| 执行 | 资产文件、检查报告、审核画廊 | 执行模型（Sonnet），依据任务文档 | 每个任务 |
| 审核 | 通过或退回 | 用户，按批次 | 每批一次 |

只覆盖轨道式光枪游戏的 3D 资产：场景、道具、角色、Boss，以及它们的受击和破坏状态。不覆盖 2D 界面、音频、玩法逻辑、宣传图。

本文的默认取值来自 2026-11-16 的确认，游戏方案可以逐项覆盖：

| 项 | 默认 |
|---|---|
| 风格 | 风格化低模，平涂色板，不用贴图 |
| 角色动画 | 小兵用分件刚体；Boss 或少数角色用骨骼片段 |
| 资产来源 | 场景和通用道具程序化生成；角色、Boss、重点道具用图生 3D；购买兜底 |
| 花费 | 本地显卡优先，线上服务只在本地不够时用；总预算 500 元以内 |
| 授权 | 内部验证，暂不以授权为门槛；仍记录来源 |
| 目标硬件 | 按安卓电视盒子或手机投屏的预算设计，PC 上运行同一套资产 |
| 审核 | 每类资产一批，每批审一次 |

## 2. 光枪游戏对美术的硬约束

这类游戏的镜头、目标和交互方式是固定的，所以能把规则写死并自动检查。这也是只做光枪游戏的好处。

| 约束 | 对美术的含义 | 落到哪里 |
|---|---|---|
| 轨道镜头，玩家不能自由走动 | 每个资产会从哪些位置、多远、什么角度被看到，可以从关卡数据算出来。只需要对这些视点负责 | 视点集（§3.3）、预算、背面剔除 |
| 所见即所中 | 看得见的部位必须打得中，打得中的部位必须看得见。模型外形要贴合命中体 | 命中契约（§3.4），检查 C01–C04、C07 |
| 目标小、时间短 | 玩家在 1–2 秒内要认出敌人、弱点、人质。轮廓和颜色角色比细节重要 | 风格包的颜色角色（§5），检查 R01–R03 |
| 限亮与白边框 | 画面亮度有上限，白边框要始终是最亮的。大面积浅色会被压成灰 | 亮度规则（§5），检查 M02、R04 |
| 每次命中都要有反馈 | 可打的东西需要受击、破坏、碎块等状态，不是一个静态模型 | 状态集（§6），检查 C06 |
| 玩法数值已调好 | 美术不能改变命中体、站位、遮挡和时间 | 改动分级（§3.5） |
| 目标硬件弱 | 面数、绘制调用、灯光、蒙皮都有预算 | 预算（§9），检查 P01–P04 |

## 3. 核心方法

### 3.1 风格靠数据和确定性后处理，不靠提示词

生成模型每次的输出风格都不一样，靠提示词和抽卡统一风格成本很高（2D 流水线里同一步骤反复迭代到第 9 版）。本框架把风格定义为数据（风格包），所有资产不论来源，都经过同一个后处理步骤（风格化器，§7.3）：统一面数、统一着色方式、把颜色吸附到色板、统一烘焙明暗。生成模型只负责给出形状，颜色和质感由风格化器决定。

平涂低模风格下，生成模型输出的贴图会被丢弃。因此只需要“图生形状”的能力，不需要高质量贴图，本地显卡的压力和失败面都小得多。

### 3.2 每个资产都有保底版本

每个资产规格单都指定一条不依赖生成模型的保底路线（程序化或拼装）。生成路线失败时按阶梯降级，流水线不会卡死：

1. 本地生成，最多换 3 个种子或 2 张概念图。
2. 线上服务，在预算闸门内（§11.4）。
3. 购买或下载现成资产，需用户同意（§11.5）。
4. 保底版本。在报告里标明该资产用的是保底版本。

### 3.3 视点集

视点集是某个资产在游戏里被看到的全部相机姿态的采样，由工具从关卡数据导出：沿轨道每 0.5 秒取一个相机姿态，记录每个资产实例在其中的距离、屏幕位置和投影尺寸。

- 场景资产用关卡视点集：只对看得到的面负责，面数预算按最近视点的投影面积定。
- 角色和道具用标准视点集：相机高 1.6 米，距离取该资产的最近和最远设计距离，水平角取 0°、±30°、±60°，俯仰取 0° 和 −15°。再加上它在关卡里实际站位的视点。
- 永远看不到的面可以删除（§7.5）。为了留余量，判断可见性时把相机位置外扩 0.5 米、视场加大 10°。

### 3.4 命中契约与白模

白模关卡和角色的命中体（由引擎的 Sim 定义）是美术的契约，不是草稿。美术在命中体和阻挡体给定的体积里填充外形：

- 角色部件：网格要贴合该部件的命中基元（球、盒、胶囊、圆柱）。允许少量超出（肩甲、帽檐），超出部分是看得见但打不中的，有上限。
- 场景：视觉上实心的东西要和阻挡体一致。子弹不能穿过看起来实心的箱子，也不能停在空气里。
- 掩体尤其严格，因为敌人躲在后面，玩家会瞄着边缘打。
- 不挡弹的装饰（栏杆、管线、吊灯）不能挡在玩家和敌人弱点之间。否则敌人看不见却能攻击，白模阶段验证过的公平性就失效了。

度量方法：在视点集的每个视点渲染两张剪影，网格剪影 V 和命中体剪影 H。

| 指标 | 定义 | 含义 |
|---|---|---|
| 可见不可打率 | \|V−H\| ÷ \|V\| | 看得见但打不中的面积比例。高了玩家会觉得判定不准 |
| 可打不可见率 | \|H−V\| ÷ \|H\| | 打得中但看不见的面积比例。对敌人是放水，对人质是冤枉 |

阈值见 §10。

### 3.5 美术改动分两级

| 级别 | 定义 | 例子 | 要求 |
|---|---|---|---|
| 只影响画面 | 不改变 Sim 的任何输入 | 换模型、换颜色、加装饰、灯光 | 同一条回放在开启和关闭美术时最终哈希相同 |
| 影响玩法 | 改变命中体、阻挡体、站位或时间 | 骨骼片段让部件移动；为了好看挪动掩体 | 重跑关卡校验器和机器人验收，重新生成回放夹具，并在方案里写明理由 |

美术数据（资产映射、颜色、灯光）单独存放，不写进玩法数据文件。否则改一个颜色就会让回放的数据哈希失效。

### 3.6 姿态只有一个来源

引擎的 Sim 是部件姿态的唯一来源，画面层只做镜像，不自己播放动画。骨骼片段也遵守这一条：在 Blender 里做好的片段被烘焙成姿态轨（每个 tick 每个部件的变换表），Sim 读表，画面跟随 Sim。这样命中体和画面永远一致，回放也保持确定。细节见 §8。

### 3.7 检查先于审核

自动检查全部通过的资产才进入审核画廊。检查结果只有四种：通过、失败、待检查、不适用。没有运行的检查不能写成通过。每个检查器都要有反例测试，证明它能抓住它该抓的问题（§10.3）。

### 3.8 可复现

- 程序化路线：同一份规格单和种子，产出的文件哈希相同。
- 生成路线：模型输出按请求指纹缓存。重跑流水线读缓存，不会悄悄重新生成。
- 改风格包后可以一键重建全部资产。

## 4. 资产分类与制作路线

### 4.1 四条路线

| 路线 | 做法 | 适合 | 特点 |
|---|---|---|---|
| P 程序化 | Blender Python 脚本按参数生成几何 | 能用参数描述的形状：墙、地面、楼梯、货架、箱子、桶、集装箱、管线 | 完全可控、可复现、面数干净。造型丰富度取决于脚本 |
| K 拼装 | 从已通过的部件库里取件组合 | 同一套部件的变体：不同兵种、不同货架摆放 | 最便宜，风格天然一致 |
| G 生成 | 概念图 → 图生 3D → 风格化器 | 有机形状、复杂机械、需要设计感的重点资产 | 造型丰富，但不可控，要靠检查和重试 |
| B 现成 | 下载免费库或购买，再过风格化器 | 生成和程序化都做不好的东西；动作库 | 需要人参与付款；风格要靠风格化器拉齐 |

### 4.2 按类别的默认路线

| 类别 | 例子 | 首选 | 保底 | 备注 |
|---|---|---|---|---|
| 场景模块 | 墙、地面、门框、平台、楼梯、货架 | P | — | 按关卡数据组装并烘焙成区块（§7.6） |
| 通用道具 | 箱子、油桶、托盘、纸箱堆 | P | — | 含破坏状态和碎块 |
| 重点道具 | 叉车、垃圾箱、办公桌 | G | P | 当掩体时必须贴合阻挡体 |
| 分件刚体角色 | 各兵种、人质 | G（整体生成后切分）或 K | P | 每个部件贴合命中基元 |
| 骨骼片段角色 | Boss | G（按部件生成后配准） | P | 片段在 Blender 里用关键帧表生成 |
| 拾取物、投射物 | 医疗包、奖章、手雷、导弹 | P | — | 小而醒目，优先保证可读 |

### 4.3 生成路线的两种用法

**整体生成后切分**（适合人形）：生成一个标准站姿的完整角色 → 按身高和关节位置对齐到骨架表 → 用关节处的平面切成部件 → 封口 → 每个部件配准到自己的命中基元。

**按部件生成后配准**（适合机械和硬表面）：每个部件单独出概念图、单独生成 → 配准到命中基元。部件之间的接缝用程序化的关节件（球、圆柱、环）遮住。

配准的做法见 §7.4。

### 4.4 生成路线的已知风险

把生成模型输出的高面数网格减面成低模，结果往往是杂乱的三角面，不像手工做的低模那样干净。这是平涂低模风格下生成路线的主要风险。应对：

- 风格化器先做体素重建和平面合并，再减面（§7.3），能缓解但不能保证。
- 框架建好后先做一次选型测试（§11.3），用数据决定生成路线对哪些类别可用。不达标的类别直接走 P 或 K，生成模型只用来出概念图给规划和审核参考。
- 任何情况下都有保底版本。

## 5. 风格包

风格包是一组数据文件，放在 `art/<游戏>/bible/`。规划模型为每个游戏写一份，执行模型不得修改。

### 5.1 色板与颜色角色

色板里每个颜色都属于一个角色。角色决定谁能用这个颜色。

| 角色 | 用途 | 规则 |
|---|---|---|
| env | 场景 | 低饱和，HSV 饱和度 ≤ 0.40 |
| identity | 每种敌人、人质、道具的识别色 | 每种一个主色，互相可分 |
| weak | 弱点 | 全游戏统一一个色系。只能出现在弱点部件上 |
| protected | 不能打的对象（人质） | 只能出现在该类对象上 |
| armor | 打不动的部位 | 中性色，可以接近场景金属色。表达“打这里没用” |
| pickup / hazard | 拾取物 / 爆炸物 | 各一个色系 |
| emissive | 灯、弱点发光 | 面积小，亮度受限 |

规则（由检查 M01–M03 执行）：

- 所有面的基色必须来自色板，并且属于该资产规格单允许的角色。
- 基色的 sRGB 亮度 Y′ ≤ 0.70。烘焙明暗之后的顶点色 Y′ ≤ 0.72。Y′ = 0.2126R + 0.7152G + 0.0722B，取 0–1 的 sRGB 值。
- env 与 identity、weak、protected、pickup、hazard 的任意两色，CIELAB 色差 ΔE ≥ 18。
- identity 之间、弱点与所在身体之间的要求见 §10 的 R 类检查。
- 色差不够的地方不能硬凑：换色，或者在游戏方案里写明用轮廓、描边、动作来区分。

### 5.2 造型与着色

风格包用数值描述造型语言，供风格化器和程序化脚本读取：

| 参数 | 含义 | 平涂低模的默认值 |
|---|---|---|
| shading | 着色方式 | flat（每个面一个法线） |
| planar_angle | 平面合并角度 | 8° |
| bevel | 硬边倒角宽度 | 0（不倒角）或 2 厘米一段 |
| min_feature_px | 最远设计距离上允许的最小独立细节 | 2 像素 |
| ao_range | 烘焙环境遮蔽的明暗范围 | 0.60–1.00 |
| gradient | 竖向渐变（脚暗头亮） | 0–10% |
| island_min_faces | 生成路线上色时的最小色块面数 | 6 |

### 5.3 材质模型

默认不用贴图，也不展 UV。颜色全部写进顶点色：顶点色 = 色板基色 × 烘焙明暗。平涂着色下每个面的顶点本来就是分开的，所以不增加顶点数。

全游戏共用极少几个材质：

| 材质 | 用途 |
|---|---|
| `mat_vc_unlit` | 静态场景。顶点色里已烘焙完整光照，运行时不计算灯光 |
| `mat_vc_lit` | 角色、道具等动态物体。顶点色是基色 × 环境遮蔽，接受一盏平行光和环境光 |
| `mat_emissive` | 发光件 |
| `mat_fx` | 透明特效 |

一个网格物体只有一个材质槽。需要发光的部分拆成单独的物体。

## 6. 资产规格单

每个资产一份 YAML，放在 `art/<游戏>/specs/`。规划模型写，执行模型照做，不得为了通过检查而修改。

```yaml
id: prop_barrel
class: prop_generic            # 类别，见 §4.2
route: P                       # 首选路线
fallback: P                    # 保底路线
generator: gen_barrel          # P 路线的脚本名；G 路线改为 concept 段
size: [0.60, 0.90, 0.60]       # 包围盒，米，X Y Z
pivot: bottom_center           # 原点位置
front: +Z                      # 正面朝向
tri_budget: 300
palette_roles: [hazard, armor]
color_regions:                 # 哪个区域用哪个色
  body: hazard_barrel
  hoops: gear
hit_contract:                  # 命中体，引用引擎数据或直接写基元
  - {shape: cylinder, radius: 0.30, height: 0.90, zone: prop}
design_distance: [4, 16]       # 最近、最远设计距离，米
states:                        # 状态集
  - intact
  - {debris: 6, max_size: 0.35}
sockets: [fx_center]           # 挂点
checks: default                # 用该类别的默认检查集，可增减
notes: 箍要一眼看得出是桶，不要做成光滑圆柱
```

生成路线的规格单把 `generator` 换成概念图要求：

```yaml
concept:
  view: three_quarter          # 人形用 front + side
  prompt: 低模风格的工业叉车，单个物体，居中，中性灰背景，平光，无文字
  must_have: [货叉, 门架, 驾驶座, 四个轮子]
  must_not: [文字, 标志, 人物]
gen_mode: whole                # whole 整体生成，parts 按部件生成
```

每个资产导出时生成一个同名的元数据文件，记录实际尺寸、面数、色块统计、挂点、状态文件列表和检查结果。`manifest.json` 汇总所有资产的来源、工具版本、种子、输入哈希、许可说明和费用。

## 7. 流水线

### 7.1 阶段

| 阶段 | 做什么 | 工具 | 产物 |
|---|---|---|---|
| S0 规格 | 校验规格单格式和引用 | artkit | — |
| S1 取源 | 按路线得到原始网格：运行生成脚本、拼装、调用生成模型、导入现成文件 | Blender / 生成适配器 | 原始网格（缓存） |
| S2 规范化 | 单位、轴向、原点、缩放到规格尺寸、应用变换 | Blender | 规范网格 |
| S3 风格化 | 清理、减面、着色方式、上色、烘焙环境遮蔽 | Blender | 风格化网格 |
| S4 配准 | 贴合命中体，切分部件，放置挂点 | Blender | 部件网格 |
| S5 状态 | 生成破坏状态、碎块；删除看不到的面 | Blender | 状态文件 |
| S6 导出 | 导出 GLB 和元数据 | Blender | `<id>.glb`、`<id>.meta.json` |
| S7 导入与检查 | Godot 导入，运行几何、颜色、契约检查；窗口模式渲染后运行可读性和性能检查 | Godot | 检查报告 |
| S8 画廊 | 生成审核画廊 | artkit | 静态网页 |
| S9 发布 | 审核通过后复制到游戏资产目录，更新 manifest | artkit | 入库文件 |

S1 之后的每个阶段都是确定的：输入相同，输出相同。

### 7.2 规范化约定

- 单位米。导出后 +Y 向上。角色和道具的正面是 +Z，与引擎姿态表一致。
- 原点按规格单的 `pivot`：角色部件在该部件命中基元的中心，道具在底面中心，场景区块在世界原点。
- 导出前应用全部变换，节点上不留旋转和缩放。
- 命名：`<类别>_<名字>[_<状态>]`，小写加下划线。节点名就是引擎查找用的名字。

### 7.3 风格化器

所有路线共用，参数来自风格包：

1. **清理**：合并重合点，删除游离几何，统一法线朝外。生成路线的网格先做体素重建，得到封闭的单层表面。
2. **减面**：先按 `planar_angle` 合并共面，再按规格单的 `tri_budget` 折叠减面，最后三角化。程序化路线的网格本来就低，通常跳过。
3. **着色方式**：按 `shading` 设置平涂或按角度平滑。
4. **上色**：每个面得到一个色板颜色。
   - 程序化路线：生成脚本给每个面打区域标签，按规格单的 `color_regions` 映射。
   - 生成路线：优先按规格单的区域规则（包围盒分区、所属部件）上色。规则不够时，把原始贴图颜色投到面上，在 CIELAB 空间吸附到允许的色板颜色，再做多数滤波，消除小于 `island_min_faces` 的碎色块。
5. **明暗**：烘焙环境遮蔽到顶点色，压到 `ao_range`，再乘上可选的竖向渐变。静态场景在 §7.6 烘焙完整光照，不在这里做。
6. **写入**：顶点色 = 基色 × 明暗。上色结果（去掉明暗的基色统计）写进元数据，供颜色检查使用。

### 7.4 配准

把来源网格贴到命中基元上：

1. 用主成分方向把网格的长轴对到基元的轴。
2. 缩放到基元的包围尺寸。整体等比缩放不限；三个方向之间的拉伸比允许在 0.8–1.25 之间，超出说明来源形状的比例不合适，判失败，不硬拉。所以概念图要按命中体的比例来画（例如引擎的人形是大头粗四肢的比例，概念图就不能画写实比例）。
3. 检查两个命中契约指标，不达标时在允许范围内微调缩放，仍不达标则失败。
4. 相邻部件之间留的缝用关节件遮住。关节件属于装饰，不参与命中，尺寸要小。

### 7.5 状态与剔除

- 破坏状态和碎块由程序化方法生成：把完整网格按平面切成若干块，封口，碎块数量和最大尺寸来自规格单。
- 弱点、受击的闪烁由引擎用材质参数实现，不做单独的网格。
- 静态场景区块按视点集删除永远看不到的面（§3.3）。角色和可移动道具不删。

### 7.6 场景组装与光照烘焙

场景不是一个个模块在引擎里实例化，而是在 Blender 里按关卡数据组装好、烘焙光照、按区域合并导出：

1. 读关卡文件的白模几何和美术布置文件（哪个白模体用哪个模块、额外的装饰件）。
2. 运行各模块的生成脚本，放到对应位置。
3. 把大面细分到最大边长 1 米左右，让顶点色能表现光照变化。
4. 按美术布置文件里的灯光，用 Cycles 把直接光和间接光烘焙到顶点色，再把亮度压到上限以内。
5. 按区域合并成区块，删除看不到的面，每个区块导出一个 GLB。

这样运行时场景不计算灯光，每个区块一次绘制调用，适合弱硬件。代价是场景不会被枪口闪光和爆炸照亮，这类反馈靠特效本身和角色身上的受光表现。

顶点色烘焙的阴影分辨率低（约 1 米），在平涂风格里通常可以接受。如果第一批场景审核认为不够，备选方案是每个区块烘焙一张光照贴图，这是唯一允许使用贴图和 UV 的例外，由游戏方案决定。

可移动的东西（角色、道具、拾取物）不烘焙光照，运行时受一盏平行光和环境光。美术布置文件给出每个区域的光色，画面层在镜头经过时插值。角色脚下用一块圆形暗片代替实时阴影。

### 7.7 导出与导入的注意事项

- 导出 GLB 时，顶点色选项要选“导出活动顶点色”，并在导出后读回文件，确认 `COLOR_0` 存在且不是全白（检查 G07）。Blender 5.2 的 glTF 导出器在多材质槽加顶点色时出过全白的问题，后来的补丁版已修复；一物体一材质槽的规则也是为了避开它。
- 一个游戏只用一个 Blender 版本和一个 Godot 版本，版本号写进 manifest。升级后全部重建并对比哈希和检查结果。
- Godot 导入设置由脚本统一写入，不手工在编辑器里调。

## 8. 角色与动画

按复杂度分三级。游戏方案为每个角色选一级，并说明理由。

### 8.1 分件刚体，公式姿态（默认）

每个部件一个网格。部件的位置由引擎姿态库的函数算出来（站、跑、蹲、瞄准等），网格跟着走。优点是不需要动画资源，命中绝对一致，美术改动只影响画面。适合士兵、机器人、带护甲的角色。角色看起来像关节玩偶，这是有意的风格取舍。

美术工作只有做部件网格。每个兵种用不同的头、躯干装备和武器来区分轮廓，四肢可以共用。

### 8.2 分件刚体，骨骼片段

部件仍然是刚体，但动作不是公式算的，而是在 Blender 里用骨架做的片段：每个部件绑一根骨头，权重全是 1。适合 Boss 这类需要有重量感和设计感动作的角色。

- **片段的来源**：规划模型在游戏方案里给出关键帧表（哪个 tick 哪根骨头在什么姿态），执行模型用脚本写进 Blender。不手工拖关键帧。现成的动作库（如 Mixamo）只适用于人形骨架，可作为 B 路线。
- **姿态轨**：每个片段按 60Hz 逐帧烘焙成表，记录每个部件相对角色根的位置和旋转。文件格式：

```json
{"format": "art3d-posetrack-v1", "rig": "mech", "hz": 60,
 "parts": ["hip", "torso", "pod_l"],
 "clips": {"walk": {"ticks": 60, "loop": true,
   "frames": [[[0, 1.9, 0, 0, 0, 0, 1], [0, 3.0, 0, 0, 0, 0, 1], [-1.7, 3.6, 0, 0, 0, 0, 1]]]}}}
```

  每帧里每个部件一个数组：位置三个数，四元数四个数。
- **引擎怎么用**：Sim 的姿态库增加“查表”这种姿态来源，按当前状态的 tick 取帧，得到部件变换，命中体和画面都用它。画面层不需要骨骼节点，也不播放动画。
- **根位移**：片段原地播放，角色在世界里的移动仍由 Sim 决定。走路片段的步幅要和 Sim 的移动速度匹配，否则会滑步。
- **这是影响玩法的改动**（§3.5）：部件会动，命中体也跟着动。游戏方案要给出弱点在可打期间的位移上限，并在接入后重跑校验器和机器人验收。
- 不参与命中的装饰件（天线、液压杆）可以放进同一张表，做更夸张的运动。

### 8.3 形变蒙皮（实验性）

网格随骨骼形变，动作最自然，自动化最难：自动绑定的质量不稳定，命中体只能近似贴合形变后的表面，蒙皮在弱硬件上也有额外开销。框架只定义接口，不承诺质量：

- 骨骼姿态同样来自姿态轨，由画面层逐帧设置到骨骼节点上。
- 命中体挂在骨头上，命中契约指标要在片段的抽样帧上逐帧检查。
- 自动绑定的候选：本地的开源绑定模型，或线上服务的绑定接口（按次计费，计入预算）。
- 只有游戏方案明确说明分件刚体不够用时才采用，并且同屏最多一个。

## 9. 目标硬件与预算

默认按移动档制作，PC 运行同一套资产。只做一档，这样开发机上审核看到的画面与目标设备基本一致。

假设的目标设备：近几年的安卓电视盒子或中端手机，支持 OpenGL ES 3，输出 1080p，目标 60 帧。对应 Godot 的 Compatibility 渲染器。

| 项 | 预算（初值） |
|---|---|
| 每帧可见三角形 | ≤ 100,000 |
| 每帧绘制调用 | ≤ 150 |
| 网格贴图 | 无（光照贴图例外时，每区块 ≤ 1024²） |
| 实时灯光 | 1 盏平行光，无实时阴影；短暂的闪光灯最多 2 盏，只照动态物体 |
| 蒙皮网格 | 同屏 ≤ 1，骨头 ≤ 32 |
| 后期效果 | 不使用环境光遮蔽、泛光和体积效果；普通的距离雾可以用 |
| 透明特效 | 同屏覆盖面积 ≤ 内容区的 1.5 倍 |

单个资产的面数预算由游戏方案按类别给出。参考范围：小兵全身 800–1,200，Boss 4,000–6,000，通用道具 50–800，重点道具 ≤ 2,000，场景区块 ≤ 25,000。

小物体不要堆面：任何资产在最远设计距离上，朝向相机的三角形平均投影面积不小于 4 平方像素。移动显卡按屏幕分块渲染，小范围内顶点密集会明显变慢。首版不做多级细节模型，靠面数预算控制。

分件刚体角色每个部件一次绘制调用，同屏角色多时绘制调用会成为瓶颈。真机测试不达标时的优化手段是让相同的部件网格合批绘制，这是引擎侧的改动，不影响资产。

**能验证和不能验证的**：流水线在开发机上用 Compatibility 渲染器运行游戏，统计每帧三角形数和绘制调用数，能证明资产在预算内、在该渲染器下显示正确。它不能证明真机帧率。真机测试需要安卓导出和设备，不在本框架内；预算数值在第一次真机测试后要重新标定。

### 10.2 结果与重试

- 结果只有通过、失败、待检查、不适用。不适用要写原因。需要窗口渲染而没跑的检查记为待检查。
- 失败后的自动重试有上限：同一资产在同一路线上最多 3 次，之后按 §3.2 的阶梯降级。
- 执行模型自己看渲染图做的目视检查只作为补充，写进报告，不能替代上表的任何一项。

### 10.3 用反例验证检查器

每个检查都要配至少一个故意做错的样本（面数超标、颜色不在色板、头比命中球大一圈、弱点和身体同色等），测试断言检查器报出对应的失败。没有反例测试的检查器不能用来放行资产。

## 11. 工具与环境

### 11.1 目录

```
gunforge3d/
  artkit/                 通用工具，与游戏无关
    artkit/               Python 包：命令行、规格单、manifest、检查、适配器、画廊
    blender/              在 Blender 里运行的脚本：生成器库、风格化器、配准、烘焙、导出
    godot/                Godot 脚本：导入检查、视点集导出、渲染检查场景
    bench/                选型测试用的固定样本
    tests/                含各检查器的反例
  art/<游戏>/
    bible/                风格包：色板、造型参数、参考图
    specs/                资产规格单
    layout/               美术布置文件：白模到模块的映射、装饰件、灯光
    reports/<批次>/       检查报告、画廊、审核表
  game/assets/art/        审核通过后入库的 GLB、元数据、姿态轨、manifest
```

原始生成物、缓存和中间文件放在仓库外（如 `D:\gunforge_cache\art3d\`），不入库。

### 11.2 运行方式

- 编排用 Python（uv 管理依赖），入口 `artkit <命令>`：`validate`（规格单）、`build <id|--all>`、`check <id|--all>`、`gallery <批次>`、`publish <批次>`、`bench`。
- Blender 一律无界面运行：`blender --background --python <脚本> -- <参数>`。脚本开头恢复出厂设置并清空场景，不依赖任何已有的 .blend 文件和用户配置。
- Godot 的几何类检查用无头模式；需要画面的检查用窗口模式，设超时。
- 每个命令可重入：已完成且输入未变的步骤直接跳过。

第一个任务先探测环境并写进报告：Blender 版本和路径、Godot 版本、显卡和显存、Python、是否有 WSL2、可用的出图工具、已配置的线上服务密钥。本文没有在开发机上验证过任何一项。

### 11.3 生成适配器与选型测试

生成模型更新很快，框架不绑定某一个模型，只定义适配器接口：输入一张或多张透明背景的图片、种子和参数，输出一个网格文件和元数据（模型名与版本、耗时、显存、是否来自缓存）。

候选（2026-11 的公开信息，执行前要重新核实）：

| 候选 | 输出 | 显存 | 备注 |
|---|---|---|---|
| TRELLIS.2 | 带材质的网格 | 官方要求 ≥ 24GB | MIT 许可。官方只在 Linux 上测试过，Windows 开发机可能要用 WSL2 |
| Hunyuan3D 2.x | 网格，可选贴图 | 只出形状约 10GB，带贴图约 29GB | 社区许可有地域和规模限制；内部验证阶段不构成障碍，但要记录 |
| TripoSG | 只有形状 | 8GB 以上 | MIT 许可。本框架不用贴图，只出形状已经够用 |
| Stable Fast 3D、TripoSR 等 | 网格 | 约 6GB | 速度快，质量较低，可作为快速预览 |

选型的首要条件是能在开发机上稳定运行，其次才是质量。因为不用贴图，优先试只出形状的模型。

**选型测试**：`artkit bench` 用 6 个固定样本（人形士兵、机械躯干、叉车、垃圾箱、带箍的桶、头盔）跑每个可用的候选，全部经过风格化器减到目标面数，记录：是否跑通、耗时、显存、几何检查通过率、风格化后剪影与概念图的吻合度，以及执行模型按固定清单做的目视评分。判定规则：

- 某个候选在某类样本上 3 次尝试至少 2 次通过几何检查且目视合格，则生成路线对该类别可用。
- 没有候选达标的类别，该游戏里一律走 P 或 K。
- 结果写成报告，在第一批审核时一并给用户看。

概念图由出图适配器生成，可以是执行环境内置的出图工具，也可以是本地的图像模型。要求：单个物体、居中、中性灰背景、平光、无文字、无地面投影；人形用正面加侧面的标准站姿。出图后自己抠成透明背景再交给生成模型，不依赖生成模型自带的抠图。

### 11.4 线上服务与预算闸门

- 总预算由游戏方案给出（默认 500 元），分成线上生成和购买两个额度。
- 只有本地阶梯走完仍失败的资产才允许用线上服务。优先选按量付费的服务，不为单个资产订阅月费。
- 每次调用前先在账本里登记预留金额，返回后记实际费用。单个资产累计上限默认 30 元，超过要用户同意。费用未知时记“未知”，不记零。
- 没有配置密钥的服务直接跳过这一级，不报错。
- 服务限流或不可用时等待并记录，不自动换另一家付费服务。

### 11.5 现成资产

- 免费且允许再利用的资源库，执行模型可以直接下载使用，记录来源和许可。
- 付费资产由执行模型提交采购建议单（要买什么、链接、价格、解决哪个资产的什么问题、不买的替代方案），用户决定并付款。
- 现成资产同样经过风格化器和全部检查。带贴图的资产按生成路线的上色方法转成色板色。
- 当前阶段不以授权为门槛。manifest 里的来源记录保证以后要商用时能逐项复查。

## 12. 批次与审核

- 游戏方案把资产分成批次，默认每类一批：道具、场景、角色、Boss。每批结束是一个停止点，执行模型提交后必须等用户回复，不得开始依赖它的任务。
- 第一批同时承担定风格的作用，所以要选最小、最便宜的一类，并附上色板和一个展示用的场景角落。第一批被退回的代价应该很小。
- 每批提交三样东西：
  - **画廊**：本地静态网页。每个资产有在游戏视点下的渲染图（最近和最远设计距离）、转台图、命中体叠加图、检查结果表。未通过和用了保底版本的排在前面。场景批次按轨道段落给出游戏内截图。
  - **审核表**：`review.yaml`，每个资产一行，用户填 `approved` 或 `rejected` 和意见。
  - **报告**：产出清单、各路线的成功率、重试次数、花费、偏离规格的地方、需要用户决定的事。
- 退回的资产按意见修改规格单（由规划模型或用户改）后重做。同一资产被退回两次，执行模型停下来说明情况，不继续盲试。

## 13. 对游戏美术方案的要求（给规划模型）

输入：游戏策划案、引擎的数据文件（关卡、角色原型、姿态表、规则）、本文。关卡数据还没有时，先按策划案估算并标明，数据出来后更新清单。

方案必须包含：

1. **边界**：沿用或覆盖 §1 的哪些默认值；与引擎方案的冲突和需要引擎配合的改动。
2. **风格包**：色板（每个颜色的角色、色值、亮度）、造型参数、设计语言（弱点、敌我、可打与不可打分别怎么表达）。色板要先用 §5.1 的规则自查，把不满足的地方和处理办法写出来。
3. **资产清单**：从数据里枚举，不凭印象。每种实体、每个部件、每个状态、每个场景区域各一项，给出类别、路线、保底、面数预算、所属批次。
4. **契约表**：每类资产的命中体或阻挡体来源，以及阈值相对默认值的调整。
5. **动画方案**：每个角色选 §8 的哪一级；骨骼片段的清单、时长、关键帧表、位移上限。
6. **预算表**：硬件预算如何分配到场景、角色、特效。
7. **批次与停止点**。
8. **花费计划**与**风险**。

任务文档的写法沿用引擎任务文档的规则：按依赖顺序切小；每个任务写明交付物、必须的测试、验收命令；不许改规格和阈值来凑通过；遇到冲突停下来报告；带停止点的任务等用户回复。

## 14. 执行规则（给执行模型）

- 只在 `artkit/`、`art/` 和 `game/assets/art/` 下工作。需要改引擎代码的接入任务在任务文档里单列。
- 规格单、风格包、阈值不是执行模型可以改的东西。认为它们有问题时写进报告。
- 没运行的检查不写通过。用了保底版本要明说。
- 生成结果一律进缓存并登记，不删除失败的尝试，报告里给出成功率。
- 涉及花钱的操作先登记预留，超过单资产上限或需要购买时停下来等用户。
- 每个任务结束写报告并跑一遍工具自己的测试。

## 15. 风险

| 风险 | 应对 |
|---|---|
| 生成网格减面后不像干净的低模 | 选型测试用数据决定生成路线的适用范围；保底版本；必要时生成模型只出概念图 |
| 程序化资产造型单调，像升级版白模 | 生成脚本提供足够的参数和细节件（箍、筋、铆钉、破损）；重点资产走生成或购买；第一批审核就暴露这个问题 |
| 顶点色烘焙的光照太粗 | 第一批场景给出顶点色和光照贴图两种样张，由用户选 |
| 分件刚体角色观感僵硬 | 这是已确认的风格取舍；用姿态、受击反馈和轮廓设计弥补；个别角色可升级到骨骼片段 |
| 骨骼片段改变命中体，破坏已调好的难度 | 位移上限、重跑机器人验收、与关闭片段的版本对比 |
| 移动端预算是估算 | 明确标为初值；尽早做一次真机测试并重新标定 |
| 本地生成模型在 Windows 上装不起来 | 环境探测；WSL2；只出形状的轻量模型；线上兜底 |
| 工具版本升级导致输出变化 | 版本写进 manifest；升级后全量重建并对比 |

## 16. 待验证的假设

1. 开发机上 Blender 的版本和无界面运行、Cycles 用显卡烘焙顶点色可用。
2. 至少一个本地图生 3D 模型能在开发机上稳定运行。
3. Godot 的 Compatibility 渲染器下，顶点色不计光照的材质、一盏平行光加顶点光照的表现符合预期。
4. 引擎愿意接受 §3.5、§3.6 的配合改动：美术数据独立存放、姿态库支持查表。
5. §9 的预算数值对实际目标设备是否合适。
