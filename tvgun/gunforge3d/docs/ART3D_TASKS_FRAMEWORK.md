# 美术框架工具 artkit 开发任务（AF00–AF13）

版本：v0.1 · 2026-11-16。依据 [ART3D_FRAMEWORK.md](ART3D_FRAMEWORK.md)（下文称“框架”）v0.5。本文是执行者（AI 编码模型）的工作说明。

本文只覆盖框架工具 `artkit` 的搭建，与具体游戏无关。引擎接入（EI）和《仓库突入》的资产制作（WR）另有任务文档，在引擎任务 T20 完成后编写。

本文描述的工具、接口和命令都是待实现的内容，没有一项在开发机上运行过。标了“预期”的接口名来自公开资料，以开发机实测为准，实测结果由 AF00 写进报告。

执行顺序：AF00 → AF01 → AF02 → AF03 → AF04 → AF05 → AF07 → AF08 → AF09 → AF10 → AF12 → AF11 → AF13 → AF06。

- 前 11 个任务完成后，工具就够第一批资产（B1）使用。
- AF11 在 Boss 的骨骼片段之前需要。
- AF13 和 AF06 只服务于生成路线的升级对比，不在关键路径上，放在最后。

## 0. 执行规则（每个任务都适用）

### 0.1 环境

- 开发机的硬件、工具路径和已验证的范围见 [DEV_ENVIRONMENT.md](DEV_ENVIRONMENT.md)。仓库根在开发机上是 `E:\tvgun`，工具根是 `gunforge3d/artkit`。实际检出路径不同时以实际为准，代码里不得写死盘符。
- 外部工具按下面的顺序查找，查找逻辑只写在 `artkit/config.py` 一处：

  | 工具 | 查找顺序 |
  |---|---|
  | Blender | 环境变量 `BLENDER_BIN` → `C:\Program Files\Blender Foundation\Blender 4.2\blender.exe` |
  | Godot | 环境变量 `GODOT_BIN` → `D:\gunforge_cache\tools\godot-4.6.3\Godot_v4.6.3-stable_win64_console.exe` |
  | 缓存目录 | 环境变量 `ARTKIT_CACHE` → `D:\gunforge_cache\art3d` |

- Python 用 3.12，依赖用 uv 管理，装在 artkit 自己的环境里。基础依赖只有 `pyyaml`、`numpy`、`pillow`，测试用 `pytest`。要加别的依赖，只能是任务里写明允许的（AF06、AF09），否则先写进进度文件，停下来问。
- 不安装、不升级 Blender、Godot、显卡驱动和系统 Python。不改动已有的 WSL 发行版。
- 在 Blender 里运行的脚本只用 Blender 自带的模块（`bpy`、`bmesh`、`mathutils`、自带的 `numpy`），不往 Blender 的解释器里装包。需要第三方库的逻辑放在 artkit 的环境里，两边用文件交换数据。
- 联网只用于三件事：uv 装包；AF09 从指定页面下载；AF06 按官方说明安装模型。不调用任何付费服务。

### 0.2 边界

- 只能新建或修改 `gunforge3d/artkit/` 下的文件和 `gunforge3d/docs/ART_PROGRESS.md`。
- 不得修改 `gunforge3d/game/`（属于引擎任务）、`gunforge3d/docs/` 下的其他文档，以及仓库里 `gunforge3d/` 之外的任何文件。
- 本文给出的数据格式、阈值和夹具内容不是执行者可以改的。认为它们有问题时写进进度文件并停下来说明。
- 不要为没有要求的功能写代码。不要添加用来绕过检查的开关。

### 0.3 代码约定

- Python：函数参数和返回值写类型标注；路径用 `pathlib`；检查和计算写成不依赖全局状态的纯函数，命令行只做参数解析和调用。
- 文本文件一律 UTF-8、LF 换行。JSON 用 `sort_keys=True, ensure_ascii=False, indent=2` 写出，末尾带一个换行。
- 哈希一律 SHA-256。对文本输入算哈希前先把 CRLF 归一为 LF，原因和引擎任务 T05 相同。
- 风格和档位的取值不写死在代码里（框架 §18.3）。预算、阈值、材质白名单从风格包、档位文件和附录 C 的默认阈值文件读。
- 可复现：随机数只用 `random.Random(seed)` 或 `numpy.random.default_rng(seed)` 的实例；不读时钟；遍历字典和场景物体前先按名字排序。
- Blender 脚本：开头调用 `bpy.ops.wm.read_factory_settings(use_empty=True)` 清空场景；参数从 `--` 之后给出的 JSON 文件读；结果写到参数指定的结果 JSON。
- Blender 的 Python 脚本抛出异常时，进程默认仍以退出码 0 结束。启动命令必须带 `--python-exit-code 1`，并且编排代码同时检查退出码和结果文件里的 `"ok": true`，两者缺一都算失败。
- Godot 脚本：不使用 `class_name`；继承 `SceneTree` 的脚本先 `await process_frame` 再操作节点；结果写到参数指定的 JSON，再 `quit(退出码)`。
- 只在逻辑不明显处写注释，注释用英文。报告和进度文件用中文。

### 0.4 测试

- 测试入口：在 `gunforge3d/artkit` 目录下执行 `uv run pytest`。退出码 0 为全部通过。
- 测试分三类，用 pytest 标记区分：

  | 标记 | 内容 | 是否在默认入口里 |
  |---|---|---|
  | （无） | 纯 Python | 是 |
  | `blender`、`godot` | 启动 Blender 或无头 Godot | 是 |
  | `window` | 启动 Godot 窗口做真实渲染 | 否。用 `uv run pytest -m window` 单独执行，结果记入进度文件 |

- 每个任务都要为新增逻辑写测试。任务里列的“必测”是下限。
- 测试必须真实断言行为。禁止为了通过而放宽断言、跳过用例，或在被测代码里识别测试环境。
- 每个检查器都要有反例测试：一个故意做错的样本，断言检查器报出对应的失败（框架 §10.3）。没有反例测试的检查器不算完成。
- 启动外部进程要设超时：Blender 默认 300 秒，Godot 默认 120 秒。超时后结束进程并判失败，不无限等待。只结束自己启动的进程。
- 涉及画面的任务还要目视自检：按任务给出的方式出图，自己查看，确认与描述相符。目视自检写进进度文件，但不能替代任何一项自动检查。
- 每个任务结束前跑一遍默认入口的全量测试，之前任务的测试不得失败。

### 0.5 提交与进度

- 每个任务完成且全量测试通过后提交一次：`git add gunforge3d/artkit gunforge3d/docs/ART_PROGRESS.md`，提交信息 `artkit: AFxx <英文摘要>`。提交到当前分支，**不 push**，不改 git 配置，不改历史。
- 不要和引擎任务的会话同时在同一个工作区里运行，两边的提交会互相干扰。需要并行时用 `git worktree` 另开一个工作区，分支名 `art/framework`，合并由用户决定。
- 提交前更新 `gunforge3d/docs/ART_PROGRESS.md`：任务号、状态、测试数量、实测结果摘要、偏离本文之处及原因、需要用户决定的事。
- 遇到本文与实际冲突、或验收无法达到时：不要绕过。在进度文件里记录问题和已尝试的做法，停下来向用户说明。

### 0.6 结果用语

检查和实测的结果只有四种：通过、失败、待检查、不适用。没有运行的不能写成通过；不适用要写原因。工具“能启动”“设备被列出”不等于“功能通过”，报告里分开写。

### 0.7 每个任务的开工与收工

- 建议每个任务用一次新的会话。不论是否新会话，开工先读：§0 全文、当前任务全文、任务引用的附录和框架小节、`ART_PROGRESS.md`。
- 开工时 `git status` 应当干净，全量测试应当通过（AF00 除外）。不是这样就先查明原因并记入进度文件。
- 只做当前任务。发现以前任务的缺陷时，可以做修复它所需的最小改动并补测试，在进度文件里写明；不要顺手重构，也不要提前实现后面任务的内容。
- 按交付项的编号逐项实现，每完成一项就写它的测试并运行，不要全部写完再一起测。
- 同一个问题用三种不同的做法都没有解决，就停下来按 §0.5 报告，不要继续盲试。
- 收工的顺序：全量测试 → 目视自检 → 更新进度文件 → 提交。

### 0.8 通用数据约定

- 单位米，角度在数据文件里用度。+Y 向上；资产的正面是 +Z。
- 向量写 `[x, y, z]`；旋转写四元数 `[x, y, z, w]`；变换写 `{"pos": [...], "quat": [...]}`；颜色写 `"#rrggbb"`，是 sRGB 值。
- 相机模型与引擎任务 T06 相同：垂直视场 `fov`，宽高比取内容区的宽除以高。内容像素 `px` 对应的射线方向是 `basis * (ndc.x * tan(fov/2) * aspect, -ndc.y * tan(fov/2), -1)` 归一化，其中 `ndc = px / 内容区尺寸 * 2 - 1`。像素 `(i, j)` 的采样点是像素中心 `(i + 0.5, j + 0.5)`。
- 每米的像素数：`内容区高 / (2 * 距离 * tan(fov/2))`。
- 所有数据文件都有 `format` 字段。读到不认识的 `format` 或多余的未知字段时报错，不要猜。
- 名字（资产 id、节点名、色板名、色区名）一律小写字母、数字加下划线。

## AF00 脚手架与环境复核

**目标**：建立可运行、可测试的空工程，并用小实验确认框架最关键的三个假设：能把光照烘焙进顶点色；顶点色能正确导出；Godot 里显示的颜色与设定一致。

**交付**

1. 工程文件：`pyproject.toml`（包名 `artkit`，`requires-python = ">=3.12,<3.13"`，命令入口 `artkit = "artkit.cli:main"`，pytest 默认参数 `-m "not window"` 并登记 `blender`、`godot`、`window` 三个标记）、`uv.lock`、`.python-version`、`.gitignore`、`README.md`（如何装环境、如何测试、目录说明，各 1–3 句）。
2. `artkit/config.py`：按 §0.1 查找工具，返回路径和版本。找不到 Blender 或 Godot 时给出明确的错误，说明如何设置环境变量。
3. `artkit/proc.py`：
   - `run_blender(script: Path, args: dict, timeout: float = 300) -> dict`。把 `args` 写成临时 JSON，命令是 `blender --background --factory-startup --python-exit-code 1 --python <script> -- <args.json>`。`args` 里自动加入 `result_path`。返回解析后的结果。退出码非 0、超时、结果文件缺失、`ok` 不为真，都抛出带日志路径的异常。
   - `run_godot(script: str, args: dict, window: bool = False, renderer: str | None = None, timeout: float = 120) -> dict`。命令是 `godot [--headless] --path <artkit/godot> [--rendering-method <renderer>] --script res://<script> -- --args=<args.json>`。引擎参数放在 `--` 之前。
   - 每次调用的标准输出和错误输出存到缓存目录的 `logs/` 下。
4. `blender/bl_common.py`：`read_args()`、`reset_scene()`、`write_result(ok: bool, **data)`。`godot/project.godot`（最小工程，窗口 1280×720）和 `godot/common.gd`（读 `--args`、写结果）。
5. `artkit/glb.py`：
   - `read(path) -> Glb`。解析 GLB 的 JSON 块和二进制块，给出：节点（名字、平移、旋转、缩放、所属网格、子节点）；每个网格图元的顶点位置、三角形索引、`COLOR_0`（转成 0–1 的浮点 RGBA）、存在哪些属性、材质名；图片和贴图的数量。
   - 支持的存储方式：浮点；归一化的无符号 8 位和 16 位；8、16、32 位索引；带 `byteStride` 的缓冲视图。遇到稀疏访问器或网格压缩扩展时报出明确的错误，不要返回错误的数据。
   - `write_simple(path, nodes)`：写出只含位置、索引、可选顶点色、可选 UV、材质名和节点变换的 GLB。它只给测试造样本用。
   - `content_hash(glb) -> str`：与封装无关的内容哈希。节点按名字排序；位置四舍五入到 1e-5，颜色四舍五入到 1e-4；包含节点名、材质名、索引。
6. `artkit/color.py`：十六进制颜色解析；sRGB 与线性互转（分段公式）；亮度 `Y′ = 0.2126R + 0.7152G + 0.0722B`（用 sRGB 值）；sRGB → XYZ（D65）→ CIELAB；色差 CIE76；HSV 饱和度。
7. `artkit env` 命令：打印一份 JSON，含工具路径和版本、显卡名称和显存（有 `nvidia-smi` 时）、缓存目录是否可写。Blender 或 Godot 缺失时退出码 1。
8. 四个实测，脚本放在 `experiments/`，结果写进 `reports/AF00/env_report.md`：

   | 编号 | 做什么 | 判定 |
   |---|---|---|
   | E1 烘焙 | 微型场景：一块地面、一个立方体、一盏平行光。地面细分到 0.1 米。用 Cycles 把漫反射的直接光和间接光烘焙到顶点色。先用 CPU，再用显卡 | CPU：立方体影子里的地面顶点比受光处暗 20% 以上。显卡：同样的判定，另记耗时 |
   | E2 导出 | 六个方块，顶点色分别是 `#000000`、`#808080`、`#b8b8b8`、`#b5483f`、`#3f8fb5`、`#d99a2b`。顶点色写成线性值，存进逐面角的浮点颜色属性，导出 GLB，用 `glb.read` 读回 | 每个方块的 `COLOR_0` 与“目标色转线性”的差 ≤ 0.004；文件里没有 UV |
   | E3 显示 | Godot 窗口模式加载 E2 的文件，材质不计光照、取顶点色，正交相机正对方块，截图 | 每个方块中心像素与目标 sRGB 值的差 ≤ 3（0–255）。用 `forward_plus` 和 `gl_compatibility` 各跑一次，两次都要通过 |
   | E4 探测 | Blender 无界面模式下 Workbench 引擎能否出图；执行环境是否有可用的出图工具，叫什么 | 只记录，不判通过或失败 |

   E1 的烘焙目标预期是 `scene.render.bake.target = 'VERTEX_COLORS'`。E2 的导出选项预期用到 `export_format='GLB'`、`export_yup=True`、`export_apply=True`、`export_texcoords=False`、`export_vertex_color='ACTIVE'`、`export_materials='EXPORT'`。这些名字以本机为准：把 `bpy.ops.export_scene.gltf.get_rna_type().properties` 列出的全部选项存到 `reports/AF00/gltf_export_options.txt`，实际用的选项写进报告。

**必测**

- `color`：`#808080` 转线性约 0.2159；`#ff0000`、`#00ff00`、`#0000ff` 的 CIELAB 分别约为 (53.24, 80.09, 67.20)、(87.73, −86.18, 83.18)、(32.30, 79.19, −107.86)，容差 0.05；黑与白的色差为 100；线性与 sRGB 往返误差 < 1e-9。
- `glb`：`write_simple` 写出再 `read` 读回，位置、索引、颜色、节点名一致。手工构造 8 位归一化颜色和带 `byteStride` 的样本，能正确读出。稀疏访问器的样本被拒绝。同一内容换一种节点顺序，`content_hash` 不变；改动一个顶点 1 毫米，`content_hash` 改变。
- `proc`：Blender 脚本里抛异常，`run_blender` 抛出异常。脚本休眠 30 秒、超时设 3 秒，调用在 10 秒内返回失败，且没有残留的 Blender 进程。
- `env`：正常环境退出码 0；把 `BLENDER_BIN` 指向不存在的路径（并屏蔽默认路径）时退出码 1。
- E2 做成带 `blender` 标记的测试，E3 做成带 `window` 标记的测试。

**验收**

- 全量测试通过。E1 的 CPU 部分、E2、E3 通过。
- E1 的显卡部分失败不阻塞，在报告里写明原因和日志位置，后续烘焙默认用 CPU。
- E1 的 CPU 部分、E2、E3 中任何一项失败：这是框架的基础假设不成立。按 §0.7 的三次规则尝试后停下来报告，不要继续后面的任务。

## AF01 数据格式与校验

**目标**：实现附录 A 的全部数据格式的读取和校验，并做出一套小夹具，供后面所有任务使用。

**交付**

1. `artkit/schema/`：每种格式一个读取函数，返回带类型的对象。校验失败时抛出列表，每条是 `<文件>:<字段路径>: <原因>`，一次报出该文件的所有问题。
2. 交叉校验 `validate_game(game_dir) -> list[str]`：
   - 档案引用的风格包和档位文件存在；基准档案存在。
   - 规格单：`class`、`route` 合法；`color_regions` 引用的色板名存在，且其角色在 `palette_roles` 里；`generator` 能在 `<游戏>/generators/` 或 `artkit/blender/generators/` 找到；`hit_contract` 里的引用能在契约数据里解析；尺寸为正；`tri_budget` 是正整数；`design_distance` 的近值小于远值；拼装规格引用的部件规格都存在。
   - 契约数据：四个文件的 `level_id`、原型名、部件名互相对得上；形状的数值有限且尺寸为正；四元数已归一化（误差 1e-6）。
3. 色板自查（框架 §5.1）：每个颜色的 `Y′` ≤ 风格包的 `base_luma_max`；`env` 角色的 HSV 饱和度 ≤ `env_saturation_max`；`env` 与 `identity`、`weak`、`protected`、`pickup`、`hazard` 任意两色的色差 ≥ `role_delta_e_min`。不满足的逐条列出。
4. 命令 `artkit validate --game <目录>`：运行以上全部校验。有错误时退出码 1。另外输出色板报告 `palette_report.md`：每个颜色的角色、色值、`Y′`、饱和度，以及角色之间的最小色差表。
5. 夹具 `tests/fixtures/minigame/`，内容按附录 B。它必须通过 `artkit validate`。

**必测**

## AF02 程序化路线的流水线：规范化、风格化器、导出

**目标**：打通程序化路线从规格单到 GLB 的全过程（框架 §7.1 的 S0–S7），带阶段缓存，结果可复现。

**交付**

1. 生成脚本的接口。生成脚本是一个 Python 文件 `gen_<名字>.py`，在 Blender 里运行，只有一个入口：

   ```python
   def build(ctx) -> None:
       """Create mesh objects in ctx.collection."""
   ```

   `ctx` 提供：`spec`（规格单）、`params`（规格单的 `params`）、`size`（包围盒尺寸）、`detail`（风格包的细节等级，整数）、`rng`（用规格单 `seed` 初始化的 `random.Random`）、`style`（风格包的 `shape` 段）、`hit`（该资产的命中基元，资产局部坐标）、`far_px_per_m`（最远设计距离上每米的像素数）、`collection`。

   生成脚本必须遵守：
   - 每个面都有色区标签。标签存成面上的整数属性 `region`，名字表存成物体的自定义属性 `regions`。用 `lib.core.set_region(bm, faces, "名字")` 设置（本任务先实现 `lib/core.py` 的这一个函数，其余在 AF05）。
   - 物体名就是导出的节点名：完整状态叫 `<id>`，发光件叫 `<id>_emissive`。
   - 物体原点在规格单 `pivot` 指定的位置，正面朝 +Z。
   - 只实现 `detail == 0`。`detail` 是别的值时抛出“未实现”。
   - 查找顺序：`<游戏>/generators/`，然后 `artkit/blender/generators/`。
2. 阶段实现，每个阶段一个 Blender 脚本 `blender/stage_*.py`，或一个脚本里分函数：

   | 阶段 | 本任务实现的内容 |
   |---|---|
   | S0 规格 | 调用 AF01 的校验 |
   | S1 取源 | 运行生成脚本 |
   | S2 规范化 | 应用全部变换；检查单位和朝向；包围盒与规格尺寸的偏差超过检查 G02 的阈值时在这里就失败 |
   | S3 整形 | 合并重合点；删除游离几何；法线统一朝外；按风格包设置平涂；三角化。输入面数超过 `tri_budget` 时走减面：先按 `planar_angle_deg` 合并共面，再折叠到预算以内。带参数 `remesh: true` 时先做体素重建（给生成路线用，本任务用高面数的合成网格测试） |
   | S4 配准 | 按规格单 `sockets` 放置挂点（名为 `socket_<名字>` 的空物体，位置由生成脚本通过 `ctx` 登记）。配准和切分留给 AF13 |
   | S5 状态 | 本任务直接通过。碎块在 AF05 |
   | S6 上色 | 见第 3 点 |
   | S7 导出 | 导出 GLB，再用 `glb.read` 读回验证，写元数据文件（附录 A.7） |

3. 上色（S6）。每个面的颜色 = 色板基色（转成线性）× 明暗：
   - 基色：面的色区标签经规格单 `color_regions` 映射到色板名。
   - 环境遮蔽：每个面从面心沿法线抬高 1 毫米，向法线半球发出 `ao_samples` 条余弦加权的射线，射程 `ao_distance_m`，用 `mathutils.bvhtree` 求交。未被挡住的比例线性映射到风格包的 `ao_range`。射线方向由“资产种子加面序号”决定，同一输入每次结果相同。这是每个面一个值，符合平涂风格；不使用 Cycles，这样结果与显卡无关。
   - 遮蔽的范围由规格单 `ao_scope` 决定：`asset`（默认，资产内所有物体互相遮挡）或 `part`（每个物体只算自己，用于会独立运动的角色部件）。
   - 竖向渐变：按面心在包围盒里的高度，从底部的 `1 - gradient` 线性过渡到顶部的 1。
   - 写入：线性颜色写进逐面角的浮点颜色属性 `Col`，设为活动属性。同一个面的各个角颜色相同。
   - 材质：每个物体一个材质槽，材质名取规格单 `material`；缺省时场景类用 `mat_vc_unlit`，其余用 `mat_vc_lit`，名字以 `_emissive` 结尾的物体用 `mat_emissive`。Blender 里的材质内容不重要，只要名字对。
4. 导出（S7）：选项用 AF00 确认过的那一组。导出后读回，确认节点名齐全、有 `COLOR_0` 且不是全白、没有 UV 和贴图、节点上没有旋转和缩放。任何一项不符就判该阶段失败，不写元数据。
5. 编排 `artkit/pipeline/`：
   - 每个阶段有指纹：上一阶段的指纹、规格单里该阶段用到的字段、风格包里该阶段用到的字段、生成脚本和 `blender/lib/` 的源码哈希、Blender 和 artkit 的版本，合起来算哈希。
   - 阶段产物存在缓存目录 `stages/<游戏>/<档案>/<id>/`：一个 `.blend` 文件，加一份规范网格摘要的哈希。摘要包含每个物体的名字、顶点（四舍五入到 1e-5）、面、每个面的色区名。
   - 指纹没变的阶段直接跳过，从最近的有效阶段继续。S6 之前的产物带着色区标签留在缓存里，换风格包的颜色只重跑 S6 和 S7（框架 §18.3）。
6. 命令：
   - `artkit build <id> --game <目录> [--profile <档案>] [--force] [--until <阶段>]`。`--all` 构建全部规格单。成品写到缓存目录 `out/<游戏>/<档案>/<id>.glb` 和 `<id>.meta.json`。
   - `artkit preview <id> --game <目录>`：用 Blender 渲染一张多视图拼图（正面、左前 45°、侧面、右后 45°、俯视 45°，共 5 格，每格 384×384），并打印数值摘要：面数与预算、包围盒与规格尺寸、色区统计。渲染用 Cycles、CPU、32 采样、固定种子；材质取顶点色，一盏平行光加均匀环境光。这个命令给规划模型看图迭代用（框架 §4.5）。
7. 一个示例生成脚本 `blender/generators/gen_crate.py`：带木条和角件的箱子，尺寸取规格单，色区 `body` 和 `trim`。

**必测**

- 夹具里的 `prop_crate`：构建成功；读回的面数 ≤ 预算；包围盒与规格尺寸的偏差 < 2 毫米；每个三角形的三个角颜色相同；材质名正确；没有 UV。

- `detail` 为 1 时构建失败，错误信息说明未实现。

**目视自检**：`artkit preview prop_crate`，确认拼图里五个视角都正常、色块分明、没有破面。

**验收**：全量测试通过；拼图存一张到 `reports/AF02/`。

## AF04 相机、软件光栅化与检查器（G、M、C、L 类）

**目标**：实现几何、颜色、契约、来源四类检查，每个检查带反例。契约检查用 artkit 自己的软件光栅化完成，不依赖显卡渲染，这样结果确定、可以无头运行、可以单测。

**交付**

1. `artkit/camera.py`：§0.8 的相机模型。`ray(px)`、`project(world)`、`px_per_meter(depth)`。
2. `artkit/views.py`：标准视点集。输入资产的包围盒和 `design_distance` 的近值、远值，输出 20 个相机：
   - 水平角取 0°、±30°、±60°，距离取近值和远值，共 10 个平视相机。相机在 `(d·sin(角), 眼高, d·cos(角))`，看向 `(0, 眼高, 0)`。眼高取 `project.yaml` 的 `eye_height`。
   - 同样的水平角和距离，再各加一个俯视相机。相机在以资产包围盒中心为球心、半径 d、仰角 15° 的位置，看向包围盒中心。
   - 资产在契约数据的 `placements` 里出现时，再加上那里列出的实际视点。
3. `artkit/raster.py`：深度缓冲的三角形光栅化，用 numpy。输入三角形、每个三角形的编号、相机、要算的像素矩形和采样倍数；输出每个采样点上最近的三角形编号和深度。采样点在像素中心；采样倍数为 2 时每个像素 2×2 个采样点。只光栅化朝向相机的面。
4. `artkit/prims.py`：射线与球、胶囊、盒、圆柱的求交，对一批射线向量化。约定与引擎任务 T04 相同：只接受 `t ≥ 0`；起点在形状内部时 `t = 0`。输出每个采样点上最近的基元编号和深度。
5. 检查器 `artkit/checks/`。每个检查是一个函数，返回 `{check, status, value, limit, detail}`。阈值从附录 C 的默认文件读，风格包的 `checks` 段可以覆盖。

   | 编号 | 判定方法 |
   |---|---|
   | G01 | 读回的三角形总数 ≤ `tri_budget` |
   | G02 | 包围盒每个方向与规格尺寸的偏差 ≤ max(3%, 2 厘米) |
   | G03 | 网格节点的平移、旋转、缩放都是单位值；挂点节点可以有平移和旋转。原点位置符合 `pivot` |
   | G04 | 没有零面积三角形（面积 < 1e-10 平方米）；没有不属于任何面的顶点。`closed: true` 的资产还要求：每条边恰好被两个面共用且方向相反；带符号的体积为正 |
   | G05 | 把网格分成连通块。每个连通块包围盒的最长边，在最远设计距离上的投影 ≥ `min_feature_px` |
   | G06 | 每个网格节点只有一个材质，名字在风格包的 `materials` 里 |
   | G07 | 每个网格节点有 `COLOR_0`，且不是全白 |
   | G08 | 没有 UV，没有图片和贴图。档位的光照方式是 `baked_lightmap` 且节点用 `mat_vc_unlit_lm` 时不适用 |
   | M01 | 每个三角形的颜色（线性）与规格单允许的某个色板颜色方向一致：两个 RGB 向量的夹角 ≤ 1.5°。最大分量小于 0.02 的近黑色跳过方向判断。场景区块的颜色里混有灯光颜色，这一项记为不适用并写明原因，改为核对元数据里的基色统计 |
   | M02 | 色板基色的 `Y′` ≤ `base_luma_max`；读回的每个三角形颜色转回 sRGB 后的 `Y′` ≤ `baked_luma_max` |
   | M03 | 命中区不是 `weak` 的部件上，没有与 `weak` 角色颜色方向一致的三角形；`protected` 角色的颜色只出现在命中区为 `hostage` 的部件上；场景类资产不使用 `identity`、`weak`、`protected`、`pickup`、`hazard` 角色的颜色 |
   | C01、C02 | 见第 6 点 |
   | C03 | 元数据里记录的每个部件的制作基准点，与契约数据里该部件在参考姿态下的 `xform.pos` 相差 ≤ 1 厘米 |
   | C04 | 见第 7 点 |
   | C05 | 规格单 `sockets` 列出的挂点节点都存在 |
   | C06 | 规格单 `states` 列出的状态节点都存在 |
   | C07 | 契约数据的每条视线（线段），与场景区块里 `solid: false` 的节点的三角形求交。有任何一条被挡住就失败，列出视线 id |
   | L01 | 清单里该资产的来源、工具版本、种子、输入哈希、许可说明、费用六项齐全。费用未知要写“未知”，不能留空 |

6. C01 和 C02 的算法。对象是一个拼装规格（角色）或单个道具。对每个姿态样本和每个视点：
   - 把每个部件的网格放到契约数据给出的 `xform` 上。镜像的部件把 X 取反并翻转三角形绕向。
   - 要算的像素矩形：网格和命中基元在屏幕上的并集包围盒，外扩 4 像素，裁到内容区。
   - 光栅化全部部件的网格，得到每个采样点上看到的部件 `vis`。对命中区不是 `none` 的部件的基元求交，得到每个采样点上打中的部件 `hit`。
   - 对每个命中区不是 `none` 的部件 P，记 V 为 `vis` 等于 P 的采样点集合，H 为 `hit` 等于 P 的采样点集合：
     - 可见不可打率 C01 = V 中“`hit` 为空，或 `hit` 的命中区与 P 不同”的比例。
     - 可打不可见率 C02 = H 中“`vis` 为空，或 `vis` 的命中区与 P 不同”的比例。
     - V 为空而 H 不空：C02 记 1。H 为空而 V 不空：C01 记 1。两者都空：该视点对 P 不适用。
   - V 与 H 的并集不足 200 个采样点时，把采样倍数加倍后重算，最多到 4 倍。
   - 每个部件取所有姿态和视点里的最坏值，与阈值比较。阈值按部件的命中区取：C01 弱点 0.10，其他 0.15；C02 人质 0.08，其他 0.15。`class` 是 `projectile` 的资产 C02 不适用。
   - 报告里写出最坏值出现在哪个姿态、哪个视点，并为它输出一张差异图：只看得见的标红，只打得中的标蓝，一致的标灰。
7. C04 的算法。对象是场景区块，视点用契约数据的验收视点：
   - 光栅化区块里 `solid: true` 的节点，得到看到的深度；对契约数据里 `solid: true` 的白模体求交，得到挡弹的深度。
   - 一个采样点两边都有、且深度差 ≤ `c04_depth_tol_m`，算一致。
   - “看着实心但不挡弹”：看得到实心面，而该方向没有白模体，或白模体比它远出容差。占“看得到实心面”的比例 ≤ 0.05。
   - “挡弹但看不见”：该方向有白模体，而看不到实心面，或实心面比它远出容差。占“有白模体”的比例 ≤ 0.10。
   - 取所有视点的最坏值。视点很多时允许先去重（位置量化到 0.25 米、朝向量化到 2°），采样倍数允许降到 0.25；这两个参数写进报告。
8. 命令 `artkit check <id|--all> --game <目录>`：按资产类别运行附录 C 里该类别的检查集，写报告（附录 A.8），有失败时退出码 1。需要 Godot 的 G09 一并运行。本任务没有实现的检查（R、P、A 类）在报告里记为待检查，不记通过。

**必测**

## AF05 细节件库与状态生成

**目标**：做出程序化造型共用的部件库。重点资产的生成脚本以后由规划模型编写，只写参数和装配，几何操作都调用这个库（框架 §4.5）。库的质量直接决定资产的质量。

**交付**

1. `blender/lib/core.py`：`set_region`、新建物体、合并、X 镜像、布尔运算、按角度或指定边倒角、收尾（合并重合点、法线朝外）、`assert_closed`。布尔和倒角用 Blender 自带的修改器，不手算顶点。
2. `blender/lib/parts.py`。每个函数返回一个网格物体，参数单位是米，每个面都带色区标签，结果是封闭网格、法线朝外：

   | 函数 | 做什么 | 主要参数 |
   |---|---|---|
   | `chamfer_box` | 切角盒 | 尺寸、切角宽度、色区 |
   | `prism` | 多棱柱和多棱台 | 边数、半径、高、收分比、色区 |
   | `slats` | 一排板条 | 总尺寸、条数、间隙、色区 |
   | `hoop` | 箍、环 | 半径、宽、厚、边数、色区 |
   | `armor_plate` | 带分缝的装甲板 | 尺寸、厚度、分缝的位置和宽度、板的色区、缝的色区 |
   | `grille` | 带框的格栅 | 尺寸、条数、条宽、深度、条的色区、框的色区 |
   | `rivets` | 一组铆钉（低面数的小棱台） | 位置列表、半径、色区 |
   | `pipe` | 沿路径的管线，可带卡箍 | 路径点、半径、边数、卡箍间距、色区 |
   | `hydraulic` | 液压杆：外筒加活塞杆 | 两个端点、内外半径、两个色区 |
   | `dent` | 凹痕和不规则变形 | 物体、种子、幅度、数量 |
   | `fracture` | 用平面把物体切成若干块并封口 | 物体、块数、种子、最大尺寸。断面的色区叫 `break` |

   规则：
   - 细节会不会小到看不见由调用方判断。库提供 `feature_visible(size_m, ctx) -> bool`，小于 `min_feature_px` 的细节不生成。`rivets`、`grille`、`hoop` 在内部调用它，不可见时返回空并说明原因。
   - `dent` 之后网格仍然封闭，顶点的位移不超过给定幅度。
   - `fracture` 的各块合起来的体积等于原物体的体积（误差 1%），每块都封闭，同一个种子结果相同。
   - 都只实现 `detail == 0`。
3. 状态生成（S5）：规格单 `states` 里有 `{debris: n, max_size: s}` 时，用 `fracture` 生成 n 个碎块，节点名 `<id>_debris_<序号>`，每个碎块的原点在自己的包围盒中心，元数据里记录它在完整状态里的位置。碎块在 S6 一起上色。
4. 示例生成脚本，与游戏无关，用来检验库和流水线：`gen_barrel`（多棱柱桶身加两道箍）、`gen_pallet`（板条托盘），并用库重写 AF02 的 `gen_crate`。夹具里的 `prop_barrel` 带 6 个碎块。
5. `docs/GENERATOR_API.md`：给规划模型看的接口说明。包括 `ctx` 的全部字段、每个库函数的签名和一张小图、色区和命名规则、怎么运行 `artkit preview` 和 `artkit check`、已知限制。写完后自己照着它从零写一个新的小生成脚本（例如一个路障），验证文档够用，这个脚本也入库。
6. 命令 `artkit lib-sheet`：把每个库函数的典型输出渲染成一张总览拼图。

**必测**

- 每个库函数：封闭、法线朝外、每个面有色区、包围盒与请求尺寸的偏差 < 1 毫米、同一参数两次生成的摘要哈希相同、面数不超过文档写明的上限。
- `feature_visible`：同一组铆钉在 5 米处生成，在 16 米处因太小而不生成。
- `dent`：位移上限成立；封闭性保持。
- `fracture`：体积守恒、块数正确、每块最长边 ≤ `max_size`、每块封闭、断面带 `break` 色区。
- `prop_barrel`：构建并通过 AF04 的全部适用检查；有 6 个碎块节点；C06 通过。删掉一个碎块后 C06 失败。
- 三个示例和按文档写的那个脚本都能构建并通过检查。

**目视自检**：`artkit lib-sheet` 的拼图，确认每个部件的形状与名字相符、没有破面。`prop_barrel`、`prop_pallet` 的预览拼图各一张。逐项对照框架 §4.5 的造型清单写下判断。

**验收**：全量测试通过；三张拼图存到 `reports/AF05/`。

## AF07 画廊、审核表与发布

**目标**：把一批资产整理成用户能审的静态网页，记录用户的决定，并在批准后安全地发布到游戏目录。

**交付**

1. 批次文件 `<游戏>/batches/<批次>.yaml`（附录 A.10）：列出这一批的资产，以及附带的东西：概念图、标杆模型的图片、同一资产的对比版本。
2. `artkit gallery <批次> --game <目录>`，输出到 `<游戏>/reports/<批次>/`：
   - `index.html`：静态网页，不依赖外部资源和脚本框架，图片用相对路径。每个资产一个区块：标准视点里最近和最远的两张图、转台图（4 个角度）、命中体叠加图、C01 的差异图、检查结果表、规格单的 `notes`。
   - 排序：有失败检查的排最前，其次是用了保底版本的，其余按 id。
   - 重点资产（`author: planner`）附概念图和各轮迭代的拼图。有对比版本的并排显示。
   - 页面顶部是这一批的汇总：资产数、通过数、失败数、待检查数、用了保底版本的数量。
   - `review.yaml`：审核表模板（附录 A.10），每个资产一行，`decision` 留空。
   - `report.md`：产出清单、检查的通过情况、重试次数、花费、偏离规格的地方。其中需要人写的段落留出标题。
3. 审核版本：对这一批的全部产物（成品文件、元数据、检查报告）和输入（规格单、风格包、契约数据）按路径排序后的“路径加哈希”再算哈希，写进 `review.yaml` 的 `review_version`。
4. `artkit publish <批次> --game <目录>`：
   - 前置条件，任何一条不满足就拒绝并说明：`review.yaml` 的 `review_version` 等于现在重新算出的值；每个资产的 `decision` 都是 `approved`；每个资产的检查全部通过，或者失败项在规格单的 `exceptions` 里预先登记过、并且审核表里对应的 `exceptions_approved` 为真。待检查的项不能发布。
   - 发布过程：先把整批文件复制到目标目录下的临时子目录并核对哈希；再移动到位；最后用“写临时文件再替换”的方式更新 `manifest.json`。中途失败时删除临时子目录，原有文件和清单保持不变。
   - 目标目录是 `<project.yaml 的 publish_dir>/<档案>/`。测试用临时目录。
5. 清单 `manifest.json`（附录 A.7）：每个已发布资产的来源、工具版本、种子、输入哈希、许可、费用、文件哈希、对应的审核版本。

**必测**

- 夹具的一批（箱子、桶、托盘）：生成画廊；`index.html` 里每个资产的图片文件都存在；汇总数字与报告一致。
- 排序：把其中一个资产改成检查失败，它排到第一个。
- 审核版本：不改任何东西重新生成，`review_version` 不变。改一个规格单再生成，`review_version` 改变。
- 发布被拒绝的各种情况，各一例：有资产未批准；审核后文件被改动；有检查失败且没有登记例外；有待检查的项；例外登记了但审核表里没有批准。
- 发布成功：目标目录里的文件哈希与来源一致，清单里有这些资产。
- 原子性：在复制阶段注入一次失败，目标目录和清单与发布前完全相同。
- L01：清单里删掉某资产的许可字段，检查失败。

**目视自检**：用浏览器打开夹具批次的 `index.html`（或截图），确认布局可读、图片都显示、失败项醒目。

**验收**：全量测试通过；画廊首页截图一张存到 `reports/AF07/`。

## AF08 场景组装与光照烘焙

**目标**：按白模数据和美术布置文件，把场景模块组装成区块，烘焙光照，导出（框架 §7.6）。

**交付**

1. 美术布置文件 `<游戏>/layout/<区块>.yaml`（附录 A.9）：白模体到模块生成脚本的映射、额外的装饰件、灯光、烘焙参数。
2. 模块生成脚本的约定：接口同 AF02。`ctx.size` 是对应白模体的尺寸，模块的实心体积必须填满这个体积，由检查 C04 判定。装饰件单独生成，在布置文件里标 `solid: false`。
3. 示例模块，只用于夹具：`gen_wall`（带踢脚和接缝的墙）、`gen_floor`（带接缝的地面）。箱子用 AF05 的 `gen_crate`，栏杆用 `pipe` 拼一个 `gen_railing`。
4. `blender/scene/assemble.py`，步骤：
   - 读契约数据的白模体和布置文件，在每个白模体的位置上运行对应的模块脚本。
   - 把大面细分到最长边不超过 `max_edge_m`。
   - 按色区上基色。
   - 烘焙光照。在场景里按布置文件建灯光，发光件作为光源。用 Cycles 把漫反射的直接光和间接光烘焙出来，不含基色。默认用 CPU；AF00 的显卡实测通过时可以用参数切到显卡。
   - 顶点色 = 基色 × 光照。然后整体缩放，使 99.9 分位的 `Y′` 不超过 `luma_max`，再把仍然超出的逐个压到上限。
   - 合并成三个节点：`<区块>_solid`、`<区块>_decor`、`<区块>_emissive`。没有内容的节点不导出。
   - 导出 GLB 和元数据。元数据里记录每个节点的 `solid`，以及去掉光照的基色统计。
5. 按视点删面（可选步骤，布置文件里 `cull: true` 时执行）：用契约数据的验收视点，把相机位置外扩 0.5 米、视场加大 10°，光栅化整个区块；在所有视点里都看不到的三角形删除。没有视点数据时不删，并在报告里写明。
6. 光照贴图的备选做法（布置文件 `bake.method: lightmap`）：给区块展一套不重叠的 UV，把光照烘焙成一张贴图（边长取档位文件的 `lightmap_px`），顶点色只存基色，材质名 `mat_vc_unlit_lm`，贴图与 GLB 同名存放。Godot 侧在 `materials.gd` 里加这个材质：不计光照，基色 = 顶点色 × 贴图。这个做法现在只需要做到能出一份样张，用户选定它之后再完善。
7. 命令 `artkit scene <区块> --game <目录>`。

**必测**

- 夹具的角落区块（地面、后墙、一个箱子、一段栏杆、一盏点光源）：构建成功；节点名正确；G、M 类适用的检查通过；C04 通过。
- 光照：离点光源最近的地面区域比最远的区域亮；箱子背光一侧的地面比受光一侧暗。
- 亮度：读回的全部颜色 `Y′` ≤ `luma_max`，容差 0.005。把灯光强度调到 10 倍，结果仍不超限。
- 细分：没有最长边超过 `max_edge_m` 的 1.1 倍的三角形。
- 可复现：CPU 连续烘焙两次，颜色的最大差 ≤ 2（0–255）。
- 删面：在后墙背后放一个从任何视点都看不到的箱子，开启删面后它的三角形被删光；看得到的三角形一个不少。
- 光照贴图：构建成功；文件带 UV 和一张贴图；G08 对它不适用；贴图里不是纯色。`window` 标记：两种做法各渲染一张，都不是纯黑。

**目视自检**：同一个视点下顶点色做法和光照贴图做法各一张图，写下两者的差别。

**验收**：默认入口和 `-m window` 的测试都通过；两张图存到 `reports/AF08/`。

## AF10 概念图适配器

**目标**：管理概念图的请求、登记和去背景。概念图是重点资产的造型参照（框架 §4.5），也是生成路线的输入。

执行模型自带的出图工具不能从 Python 里调用，所以适配器分成两半：artkit 负责生成请求、登记结果、检查和处理图片；出图这一步由执行模型用自己的出图工具完成，或者由本地的图像模型完成。

**交付**

1. `artkit concept request <id> --game <目录>`：读规格单的 `concept` 段，组装出图要求，写成请求文件 `<缓存>/concept/<指纹>/request.json`。内容包括：
   - 完整的提示词：规格单的 `prompt`，加上框架 §11.3 的固定要求（单个物体、居中、中性灰背景、平光、无文字、无地面投影），加上 `must_have` 和 `must_not`。
   - 视图：`three_quarter`，或 `front` 加 `side` 两张。
   - 比例提示：资产包围盒的宽、高、深之比。命中体是大头粗四肢的角色，要把这个比例写进提示词。
   - 指纹：以上内容的哈希。同样的请求得到同样的指纹。
2. `artkit concept import <id> <图片> --tool <工具名> [--seed <种子>]`：把出好的图登记到该请求下。记录工具名、种子、图片哈希、时间之外的全部信息。同一个请求可以登记多张，按登记顺序编号。
3. 自动检查，登记时运行，结果写进登记记录：
   - 图片最短边 ≥ 768 像素。
   - 背景均匀：四条边上各取一圈像素，颜色的标准差低于阈值，并且接近中性灰。
   - 主体居中：前景包围盒的中心离图片中心不超过边长的 10%，四周留白不少于 5%。
   - 单个主体：前景的最大连通块占全部前景面积的 90% 以上。
   - 有没有文字、内容对不对，自动检查判断不了。由执行模型看图后在登记记录里填写目视结论。
4. 去背景：从四条边向内对接近背景色的像素做连通填充，得到透明背景的 PNG，边缘做 1 像素的羽化。纯计算，不依赖模型。输出 `<编号>_cutout.png`。
5. `artkit concept list --game <目录>`：列出每个需要概念图的资产的状态：未请求、已请求未登记、已登记及检查结果。
6. 可选的本地出图后端。只有在开发机上已经装有可用的本地图像模型时才接入，不为此安装新模型。没有就不做，在报告里写明。
7. AF00 的 E4 记录了执行环境有没有出图工具。两种后端都没有时，本任务做完第 1–5 点后停下来报告，由用户决定用什么出图。

**必测**

- 请求：同一规格单两次生成的指纹相同；改一个字，指纹改变；提示词里包含全部固定要求和比例提示。
- 自动检查，用程序合成的图片：灰底上一个居中的色块通过；偏到角上的失败；背景是渐变的失败；两个分开的色块失败；512 像素的失败。
- 去背景：灰底色块的图，输出里背景像素的透明度为 0，色块内部为 255；色块内部有一块与背景同色的区域时，它不被挖掉。
- 登记：登记两张后列表显示两条；重复登记同一张图被识别并拒绝。

**目视自检**：有出图工具时，用夹具里的一个规格单实际走一遍：请求、出图、登记、去背景，把原图和去背景的结果各存一张，写下目视结论。没有出图工具时这一步记为待检查。

**验收**：全量测试通过；`reports/AF10/` 里有一份说明当前可用的出图方式的记录。

## AF12 可读性与性能检查的判定部分（R 类、P03）

**目标**：实现 R01–R04 和 P03 的判定函数。它们都是对图片和几何的纯计算，现在就能用合成数据测试。在引擎里取帧、统计每帧的三角形数和绘制调用数（P01、P02、P04）要等引擎接入，写在引擎接入的任务文档里。

**交付**

1. 取帧包的格式（附录 A.11）：一组游戏画面，每帧带限亮前和限亮后的图片、相机、以及画面里每个实体的原型、姿态和根变换。本任务只定义格式和读取，不负责产生它。
2. 目标掩码：用 AF04 的软件光栅化，按取帧包里的相机和实体变换算出每个实体、每个部件在这一帧里的像素掩码。实体之间和场景的遮挡要算进去，被挡住的像素不在掩码里。
3. 判定函数 `artkit/checks/readability.py`。颜色统计都在 CIELAB 里做：先把像素转成 CIELAB，再取平均，色差用 CIE76。使用限亮后的图片，R04 除外。

   | 编号 | 判定方法 | 默认阈值 |
   |---|---|---|
   | R01 | 目标掩码内的平均色，与掩码外 12 像素环带内的平均色的色差。环带里属于其他实体的像素不算 | ≥ 20 |
   | R02 | 弱点部件掩码内的平均色，与同一实体上相邻部件掩码内的平均色的色差；弱点部件掩码的等效半径 `sqrt(面积/π)` | 色差 ≥ 20；半径不小于规格给的最小像素 |
   | R03 | 两种原型各取一帧最远设计距离上的掩码，缩放到相同高度、质心对齐后的交并比；以及两者掩码内平均色的色差。人质与任一敌人只看色差 | 交并比 ≤ 0.80 或色差 ≥ 25；人质与敌人色差 ≥ 35 |
   | R04 | 限亮前图片 `Y′` 的 99.9 分位 | ≤ `project.yaml` 的 `luma_cap` |

   相邻部件由契约数据决定：两个部件的命中基元表面距离小于 5 厘米即为相邻。
4. P03：资产放在最远设计距离、用标准视点集的平视相机，朝向相机的三角形的平均投影面积 ≥ 档位文件的 `min_tri_px2`。纯几何计算，不需要图片。
5. 把这些检查接进 `artkit check`：有取帧包时运行 R 类，没有时记为待检查。P03 总是运行。P01、P02、P04 记为待检查，原因写“需要引擎接入”。

**必测**

- 掩码：两个实体一前一后，后面那个被挡住的部分不在它的掩码里。
- R01：合成一帧，灰色背景上一个红色目标，通过；目标改成与背景相差很小的灰色，失败。环带里有另一个实体时，它的像素不参与平均。
- R02：头和躯干同色，失败；不同色通过；头的掩码小于最小像素，失败。
- R03：两个形状和颜色都相同的原型失败；形状相同、颜色不同的通过；颜色相同、形状明显不同的通过。人质与敌人色差 30，失败。
- R04：限亮前图片里千分之二的像素是纯白，失败；千分之零点五是纯白，通过。
- P03：一个 2 万面的小球在 16 米处失败；一个 12 面的盒子通过。
- 没有取帧包时，R 类的状态是待检查，不是通过。

**验收**：全量测试通过。

## AF11 姿态轨与动画检查（A 类）

**目标**：把规划模型写的关键帧表求值成姿态轨（框架 §8.2），并实现 A01–A03。姿态轨是玩法数据，会进入回放的哈希，所以求值必须是纯计算、逐位可复现。Blender 只用来渲染预览，不参与求值。

**交付**

1. 关键帧表的格式和求值规则，见附录 A.12。
2. `artkit/posetrack/evaluate.py`：把关键帧表求值成框架 §8.2 的 `art3d-posetrack-v1`。每帧每个部件输出相对角色根的位置和四元数，数值四舍五入到 1e-6，四元数归一化并取 `w ≥ 0` 的那个符号。
3. `artkit/posetrack/validate.py`：按框架 §8.2 校验姿态轨文件。`frames` 的长度等于 `ticks`；每帧的部件数等于 `parts` 的长度；部件名唯一；拒绝非有限数、未归一化的四元数、未知部件、缺帧。
4. 检查：

   | 编号 | 判定方法 |
   |---|---|
   | A01 | 片段长度是整数 tick。循环片段从末帧到首帧，每个部件的位移和转角不超过片段内部相邻帧最大步长的 1.5 倍 |
   | A02 | 关键帧表里登记的每个连接点（两个部件各给一个局部锚点），在每一帧上两个锚点的世界距离 ≤ 3 厘米 |
   | A03 | 关键帧表的 `limits` 段给出：哪些片段里、哪些部件，相对静止位置的位移上限和速度上限。逐帧核对。速度 = 相邻两帧的位移 × 60 |

5. 命令 `artkit posetrack build <关键帧表> --out <姿态轨>` 和 `artkit posetrack check <关键帧表>`。
6. 预览：`artkit posetrack preview <姿态轨> --game <目录> --clip <片段>`。Blender 读姿态轨，把每一帧的变换套到各部件的网格上（没有网格时用契约数据里的命中基元代替），每隔若干帧渲染一格，拼成一张图。
7. 夹具：一个三部件的小骨架（底座、躯干、手臂），带一个循环片段和一个非循环片段。

**必测**

- 求值：只有一个部件、两个关键帧、线性插值时，中点的位置是两端的平均、旋转是球面插值的中点。`smooth` 缓动时，首尾两帧的步长小于中段步长的 20%。
- 层级：父部件旋转 90° 时，子部件的世界位置跟着转到正确的位置。
- 循环：循环片段的第 0 帧不重复出现在末尾；按 `tick % ticks` 取帧首尾相接。
- 可复现：同一份关键帧表两次求值，输出文件逐字节相同。
- 校验：缺一帧、多一个部件、含 NaN、四元数未归一化，各被拒绝。框架 §8.2 里那个只有一帧的缩略例子被拒绝。
- A01：末帧到首帧有一个大跳变的循环片段失败。
- A02：让手臂的锚点离开躯干 5 厘米，失败。
- A03：位移上限 0.10 米，某帧位移 0.12 米，失败；位移合格但某两帧之间的速度超限，失败。

**目视自检**：夹具循环片段的预览拼图一张，确认动作连贯。

**验收**：全量测试通过；预览图存到 `reports/AF11/`。

## AF13 配准与部件切分

**目标**：把来源不受控的网格（图生 3D 的输出、现成资产）贴到命中基元上，并把整体的人形切成部件（框架 §4.3、§7.4）。只有生成路线和现成资产用得到。

**交付**

1. `blender/register/fit.py`：把一个网格配准到一个命中基元。
   - 用主成分方向把网格的长轴对到基元的轴。球形基元不需要对轴。
   - 缩放到基元的包围尺寸。整体等比缩放不限；三个方向之间的拉伸比必须在 0.8–1.25 之间，超出就判失败，不硬拉。
   - 算 C01 和 C02（用 AF04 的算法和标准视点集）。不达标时在拉伸比允许的范围内微调缩放，最多 8 步。仍不达标判失败。
   - 返回：是否成功、最终的缩放和拉伸比、两个指标的值。
2. `blender/register/slice.py`：把一个标准站姿的人形网格切成部件。
   - 输入：网格、切面表（每个切面给出位置、法线、把哪一侧分给哪个部件）。切面表由规格单给出。
   - 先把网格按身高缩放、脚底对齐到原点、正面朝 +Z。
   - 用切面依次切开，每个切口封口，封口面的色区叫 `cap`。
   - 每个部件再用 `fit` 配准到自己的命中基元。
   - 输出每个部件一个物体，原点在该部件命中基元的中心。
3. 把这两步接进流水线的 S4：规格单 `route` 是 G 或 B 时执行；`gen_mode: whole` 时先切分再配准，`parts` 时只配准。
4. 关节件：相邻部件之间的缝用 AF05 的 `prism` 或球形件遮住。尺寸取相邻两个基元在连接处的较小截面的 0.8 倍，命中区是 `none`，不参与 C01 的分母以外的计算。

**必测**

- 配准，用程序合成的网格：
  - 一个被随机旋转过的长椭球，配准到胶囊基元后，长轴与胶囊轴的夹角 < 3°，C01 和 C02 达标。
  - 一个长宽比 3:1 的盒子配准到立方体基元，因拉伸比超限而失败，返回值里有实际需要的拉伸比。
  - 微调：一个略大的球配准到球形基元，微调后 C01 从超标降到达标。
- 切分：用几个基本体合并成一个“人形”（球头、盒躯干、圆柱四肢），按切面表切开。得到规定数量的部件；每个部件封闭；封口面带 `cap` 色区；各部件体积之和等于原体积（误差 2%）；每个部件的原点在对应基元的中心（C03 通过）。
- 流水线：一个 `route: B` 的夹具规格，以文件形式提供一个合成网格，能走完 S1–S7 并通过 G 类和 C 类检查。

**验收**：全量测试通过。

## AF06 生成适配器、缓存、预算账本与选型测试

**目标**：定义图生 3D 的适配器接口，实现缓存和预算账本，并在开发机上试装候选的本地模型（框架 §11.3、§11.4）。这是风险最大的一个任务：模型可能一个都装不上。装不上不算任务失败，如实报告即可。

   - 判定：某个后端在某类样本上 3 次里至少 2 次几何检查通过且三项目视都为是，该类别记为“可做生成版本”。
   - 输出 `reports/AF06/bench_report.md` 和一份机器可读的结果。
6. 试装本地模型。规则：

   - 排序：能在 Windows 上原生运行的优先；只输出形状的优先；显存需求不超过开发机的优先。

   - 许可不允许当前用途、或看不明白的，不安装，记为“许可待核验”。
7. 命令 `artkit gen <id> --game <目录>`：按规格单调用可用的后端生成，结果进缓存。没有可用后端时明确报告并以退出码 1 结束，流水线的其余部分不受影响。

**验收**

- 全量测试通过。

## 附录 A：数据格式

每个文件都有 `format` 字段。下面的例子都是完整合法的写法，除非注明是片段。

### A.1 游戏配置 `<游戏>/project.yaml`

```yaml
format: art3d-project-v1
game: minigame
camera: {fov_deg: 60, content_px: [1776, 936], near: 0.1, far: 200}
eye_height: 1.6
luma_cap: 0.75
publish_dir: ../../../game/assets/art     # 相对本文件
budget: {total: 500, online: 300, purchase: 200, per_asset: 30}
```

### A.2 风格包 `<游戏>/bible/<名字>.yaml`

```yaml
format: art3d-style-v1
id: flat
material_model: flat_vertex_color      # 目前只实现这一种
detail: 0                              # 目前只实现 0
materials: [mat_vc_unlit, mat_vc_lit, mat_emissive, mat_fx]
shape:
  shading: flat
  planar_angle_deg: 8
  bevel_m: 0.0
  min_feature_px: 2
  ao_range: [0.60, 1.00]
  ao_distance_m: 1.0
  ao_samples: 64
  gradient: 0.05
  island_min_faces: 6
limits:
  base_luma_max: 0.70
  baked_luma_max: 0.72
  env_saturation_max: 0.40
  role_delta_e_min: 18
palette:
  - {name: env_wall, role: env, hex: "#767c85"}
  - {name: amber, role: weak, hex: "#c98a2a"}
checks: {}                             # 覆盖附录 C 的默认阈值，键名相同
```

`role` 只能是 `env`、`identity`、`weak`、`protected`、`armor`、`pickup`、`hazard`、`emissive`、`gear`。`gear` 是装备和箍这类中性深色，规则同 `armor`。`material_model` 或 `detail` 是未实现的取值时，校验通过，但构建时报“未实现”。


### A.5 规格单 `<游戏>/specs/<id>.yaml`

单个资产：

```yaml
format: art3d-spec-v1
id: prop_barrel
class: prop_generic
route: P
fallback: P
author: executor
generator: gen_barrel
params: {sides: 12, hoops: 2}
seed: 1
size: [0.60, 0.90, 0.60]
pivot: bottom_center
front: +Z
tri_budget: 300
closed: true
palette_roles: [hazard, gear]
color_regions: {body: hazard_barrel, hoops: gear_dark, break: gear_dark}
material: mat_vc_lit
ao_scope: asset
hit_contract:
  - {zone: prop, shape: {type: cylinder, pos: [0, 0.45, 0], quat: [0, 0, 0, 1], radius: 0.30, half_height: 0.45}}
design_distance: [4, 16]
states: [intact, {debris: 6, max_size: 0.35}]
sockets: [fx_center]
checks: default
exceptions: []
notes: 箍要一眼看得出是桶
```

字段说明：

| 字段 | 取值与规则 |
|---|---|
| `class` | `scene_module`、`prop_generic`、`prop_hero`、`char_part`、`char_assembly`、`pickup`、`projectile` |
| `route`、`fallback` | `P`、`K`、`G`、`B`。`char_assembly` 必须是 `K` |
| `author` | `executor`（默认）或 `planner`。`planner` 的生成脚本执行模型只运行，不改造型 |
| `pivot` | `bottom_center`、`center`、`origin` |
| `closed` | 是否要求封闭网格。角色部件和道具必须为真 |
| `hit_contract` | 直接写基元，或写引用 `{ref: "<原型>/<部件>"}`，从契约数据取该部件在参考姿态下的基元 |
| `checks` | `default`，或 `{add: [...], remove: [...]}`。`remove` 里的每一项必须同时出现在 `exceptions` 里 |
| `exceptions` | 预先登记的例外：`{check, scope, limit, reason}`。由规划模型写，执行模型不得添加 |
| `concept`、`gen_mode`、`upgrade` | 见框架 §6 |

拼装规格（一个角色）：

```yaml
format: art3d-spec-v1

parts:
  head: {asset: part_dummy_head}
  torso: {asset: part_dummy_torso}
  leg_l: {asset: part_dummy_leg}
  leg_r: {asset: part_dummy_leg, mirror_x: true}
design_distance: [5, 11]

checks: default
exceptions: []
```

### A.6 契约数据 `<游戏>/contract/`

四个文件，由引擎侧的导出工具产生（任务 EI07）。框架工具只读不写。形状的写法：

```
球    {"type": "sphere", "center": [x,y,z], "radius": r}
胶囊  {"type": "capsule", "a": [x,y,z], "b": [x,y,z], "radius": r}
盒    {"type": "box", "pos": [x,y,z], "quat": [x,y,z,w], "half": [hx,hy,hz]}
圆柱  {"type": "cylinder", "pos": [x,y,z], "quat": [x,y,z,w], "radius": r, "half_height": h}    轴线是局部 Y
```

`hit_parts.json`：每个原型在若干姿态样本下，每个部件的变换和命中基元。坐标相对角色根（脚底中心，正面 +Z）。`xform` 是画面层放置该部件网格用的变换。

```json
{
  "format": "art3d-contract-hit-v1",
  "game": "minigame",
  "source": {"sim_revision": "fixture", "archetypes_sha256": "fixture"},
  "archetypes": {
    "dummy": {
      "team": "enemy",
      "reference": {"pose": "idle", "t": 0.0},
      "samples": [
        {"pose": "idle", "t": 0.0, "parts": [
          {"name": "head", "zone": "weak",
           "xform": {"pos": [0, 1.60, 0], "quat": [0, 0, 0, 1]},
           "shape": {"type": "sphere", "center": [0, 1.60, 0], "radius": 0.17}}
        ]}
      ]
    }
  }
}
```

`zone` 只能是 `weak`、`body`、`armor`、`hostage`、`prop`、`none`。上例的 `parts` 是片段，完整文件要列出该原型的全部部件。

`whitebox.json`：关卡的白模体，世界坐标。

```json
{
  "format": "art3d-contract-whitebox-v1",
  "level_id": "mini",
  "items": [
    {"id": "floor", "kind": "geometry", "solid": true, "segment": null,
     "shape": {"type": "box", "pos": [0, -0.1, -5], "quat": [0, 0, 0, 1], "half": [4, 0.1, 6]}}
  ]
}
```

`views.json`：相机采样，以及实体在哪些视点里出现。

```json
{
  "format": "art3d-contract-views-v1",
  "level_id": "mini",
  "purpose": "acceptance",
  "views": [
    {"id": "s1@0", "segment": "s1", "tick": 0, "pos": [0, 1.6, 0], "look": [0, 1.5, -10], "fov_deg": 60}
  ],
  "placements": [
    {"entity": "s1_d1", "archetype": "dummy", "pose": "idle", "t": 0.0,
     "root": {"pos": [0, 0, -8], "quat": [0, 0, 0, 1]}, "views": ["s1@0"]}
  ]
}
```

`sightlines.json`：关卡校验器检查过的“相机到暴露弱点”的视线。

```json
{
  "format": "art3d-contract-sightlines-v1",
  "level_id": "mini",
  "lines": [
    {"id": "s1_d1@s1@0", "view": "s1@0", "from": [0, 1.6, 0], "to": [0, 1.6, -8], "target": "s1_d1/head"}
  ]
}
```

### A.12 关键帧表

```yaml
format: art3d-keyframes-v1
rig: mini_rig
hz: 60
parts:                      # rest 是静止姿态，相对角色根
  - {name: base, parent: null, rest: {pos: [0, 0.5, 0], quat: [0, 0, 0, 1]}}
  - {name: torso, parent: base, rest: {pos: [0, 1.5, 0], quat: [0, 0, 0, 1]}}
  - {name: arm, parent: torso, rest: {pos: [0.6, 1.8, 0], quat: [0, 0, 0, 1]}}
joints:
  - {a: base, a_anchor: [0, 0.5, 0], b: torso, b_anchor: [0, -0.5, 0]}
clips:
  sway:
    ticks: 60
    loop: true
    keys:
      - {tick: 0, part: torso, pos: [0, 0, 0], rot_deg: [0, 0, 0], ease: smooth}
      - {tick: 30, part: torso, pos: [0, 0.02, 0], rot_deg: [0, 0, 5], ease: smooth}
limits:
  - {clips: [sway], parts: [torso], max_disp_m: 0.10, max_speed_mps: 0.3}
```

求值规则：

- 每个部件的局部静止变换 = 父部件静止变换的逆 × 自己的静止变换。没有父部件的直接用自己的。
- 关键帧的 `pos` 和 `rot_deg` 是在局部静止变换之上叠加的偏移：局部变换 = 局部静止变换 × 平移(`pos`) × 旋转(`rot_deg`)。旋转绕部件自己的原点。`rot_deg` 是 X、Y、Z 三个角，按先 X、再 Y、再 Z 的顺序依次绕部件的局部轴旋转，换算成四元数后再插值。
- 同一个部件相邻的两个关键帧之间：位置线性插值，旋转球面插值（取较短的弧）。插值用的时间先经过后一个关键帧的 `ease`：`linear` 不变，`smooth` 用 `3t² − 2t³`。
- 第一个关键帧之前保持第一个关键帧的值，最后一个之后保持最后一个的值。循环片段必须在 tick 0 有关键帧，最后一个关键帧到 tick `ticks` 之间按回到 tick 0 的值插值。
- 没有关键帧的部件保持静止姿态。
- 世界变换沿层级从根往下乘。输出是每个部件相对角色根的绝对变换，不是相对静止姿态的偏移。
- `a_anchor`、`b_anchor` 是各自部件局部坐标里的点。

## 附录 D：常见坑

- Blender 的 Python 脚本出错时进程退出码默认是 0。启动命令带 `--python-exit-code 1`，并检查结果文件。
- `--factory-startup` 下没有任何扩展和用户设置，这是有意的。需要扩展时只用 AF09 验证过的加载方式。
- Blender 的浮点颜色属性存的是线性值；色板的色值是 sRGB。写入前转线性，检查时转回来。不要把线性数值直接和 sRGB 阈值比。
- 平涂着色下同一个顶点在不同的面上颜色不同，颜色属性要用“面角”域，不能用“顶点”域。
- Blender 是 Z 轴向上，导出时转成 Y 轴向上。检查朝向时以读回的 GLB 为准，不以 Blender 场景里的数值为准。
- Godot 无头模式没有渲染，取不到画面。需要画面的一律用窗口模式，并设超时。由 Agent 在后台启动的窗口拿不到焦点属于正常，脚本里不要依赖焦点。
- 继承 `SceneTree` 的 Godot 脚本，`_initialize()` 里根节点还不在树内。先 `await process_frame`。
- PowerShell 里调用带空格路径的程序要用 `&`。Godot 的引擎参数放在 `--` 之前，脚本参数放在之后。
- numpy 的大数组广播很容易占满内存。光栅化按三角形的屏幕包围盒处理，射线求交按批处理。
- 写 JSON 时不要把 `numpy` 的数值类型直接交给 `json`，先转成 Python 的 `float` 和 `int`。
- 缓存目录在仓库外。测试用临时目录当缓存，不要读写真实的缓存目录。
